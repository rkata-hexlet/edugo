# Эпизод 08 «Двойное списание» — разбор tech-expert до сценария (24.10)

Тема — идемпотентность запроса (Idempotency-Key) в сервисе оплаты. Мир новый, «сервис оплаты», на 08–09 (09 —
transactional outbox). Чек-лист `06-recurring-mistakes.md` в ветке ещё не лежал — прогнать по сценарию отдельно.

## 0. Главное
- Самая честная причина двойного списания — **ответ потерян, клиент повторяет, а первый запрос ещё в работе или уже
  списал**. Повтор и гонка — один сценарий. «Нет ответа» — это не «не прошло», а **итог неизвестен**.
- Рифма с 01: там «двойной эффект гасит приёмник по ключу». В 08 приёмник — мы, а в кейсе 2 мы ещё и отправитель —
  ключ надо передать дальше в банк. Финал: **ключ работает по всей цепочке**.

## 1. Модель мира
- **Приложение** (слева): «Оплатить», спиннер, экран результата. Ключ генерирует **один раз на попытку оплаты** (UUID при
  открытии экрана оплаты), хранит до итога и шлёт в каждом повторе. Носитель — ключ на запросе.
- **Поды A, B** сервиса оплаты на Go: повтор может попасть на другой под (балансировщик).
- **Postgres**: `payments(id, order_id, amount, status)`; `idempotency_keys(user_id, key, status, response, locked_until)`
  с `UNIQUE(user_id, key)`, `status` `processing`/`done`, `response` — сохранённый ответ («200 · оплачено»),
  `locked_until` — только в кейсе 2. `request_hash` — в описание. Совет: сразу отдельная таблица ключей.
- **Банк / эквайер** (справа, вне таблицы, как «Почта» 01) — журнал списаний «−990 ₽ · заказ 7»; дубль — красным.
  Внешний эффект, транзакцией не откатить.
- **Часы БД** — только в кейсе 2.
- Для 09: после оплаты сервис должен сообщить «оплачено» наружу — в 08 **не показывать**.
- Упрощения (в описание): авторизация+capture одним шагом; банк = PSP (ЮKassa/Stripe); дубль можно вернуть (refund) —
  голосом не «деньги потеряны».

## 2. Хук
| причина | частота | картинка | вердикт |
|---|---|---|---|
| Таймаут / обрыв ответа → повтор | самая частая | видно, что списание уже было, ответ потерялся назад | **брать** |
| Двойной тап | часто | зритель придумает «заблокировать кнопку» | только репликой |
| Ретрай балансировщика/прокси/SDK | реже для POST | nginx по умолчанию не повторяет POST (`non_idempotent`) | в описание |

Картинка: «Оплатить» → под A → банк «−990 ₽» → `succeeded` → ответ рвётся → «Ошибка сети. Повторить?» → под B → второе
«−990 ₽» красным. Ключа в хуке нет. Фраза: «ответа нет — это не "нет", это "неизвестно"».
Хук — по оборванному ответу; кейс 1.1 — повтор, пока первый ещё ждёт банк (таймаут приложения меньше хвоста банка).

## 3. Арка
- **(а) SELECT → INSERT по заказу** — брать. INSERT платежа после ответа банка ⇒ повтор во время ожидания банка видит
  пусто. Check-then-act (рифма с 01).
- **(б) UNIQUE на ключ + `INSERT … ON CONFLICT DO NOTHING` первым шагом, COMMIT до банка** — брать (рифма с CAS 01). Не
  решает «что ответить повтору».
- **(в) сохранённый ответ (replay)** — ядро. Наивное (б) отвечает «ключ уже использован» → пользователь видит «не
  прошло» при списанных деньгах, платит заново → **новый ключ** → второе списание без гонки.
- **(г) `processing` → 409 «ещё в работе»** — внутри (в): та же развилка по `status`. Клиент ждёт и повторяет с тем же
  ключом.
- **(д) другое тело → 422** — в описание.
- **(е) упали между банком и записью → ключ в банк** — кейс 2; перед ним «ключ завис в `processing`» (рифма с 01 2.1).
- **(ж) срок жизни ключей** — в описание; одной фразой в кейсе 2 («банк помнит ключ сутки»).

Не хватало:
1. **Почему не `UNIQUE(order_id)`?** Отказ банка и повтор другой картой — законная вторая попытка; ключ различает
   «повтор того же запроса» и «новую попытку»; UNIQUE не говорит, что ответить повтору. Одна фраза в 1.2.
2. **Ключ — на попытку оплаты, не на HTTP-попытку** (самый частый баг). Ложится на кадр «новый ключ → второе списание».
3. Область ключа `(user_id, key)` — в описание.
4. Какие ответы сохранять (окончательные — да, наши 5xx до эффекта — нет) — в описание.
5. Go: `r.Context()` отменяется при обрыве клиента → обрывает вызов банка → кейс 2 без падения пода. Лекарство —
   `context.WithoutCancel`. В описание или фразой кейса 2.
6. Сверка с банком (reconciliation), вебхуки — в описание.

Частота: (а) ≈ (в) > (б) > (е) > (г) > (ж) > (д).

## 4. Ловушки
1. «База видит повтор» — нет: UNIQUE отклоняет вставку, решение «повтор → сохранённый ответ» принимает под.
2. Захват ключа в одной транзакции с вызовом банка: второй INSERT ждёт на уникальном индексе — выглядит «работает»; но
   при падении первого ключ исчезает → второе списание; соединение занято на время банка. Только COMMIT захвата до банка.
3. `ON CONFLICT DO NOTHING RETURNING` при конфликте строку не возвращает — ответ отдельным SELECT; на RC видно, на RR в той
   же транзакции — нет. SQL-панель — два оператора в autocommit, уровень не называть.
4. Запись результата — одной транзакцией (`payments` + `done, response`).
5. 409 — не отказ, а «подождите»: жёлтый/нейтральный. Красным — только «ключ уже использован».
6. Перехват зависшего ключа по сроку = повтор вызова банка → двойное списание. Lease не решение, только делает повтор
   возможным; безопасным его делает ключ у банка.
7. Ключ в банк — не обязательно ключ клиента, но тот же при каждом повторе (Brandur — производный от нашей записи). В
   кадре тот же ключ — допустимо.
8. Ключ у банка живёт ограниченно (ЮKassa 24 ч, Stripe ≥ 24 ч) — не «никогда не спишем дважды».
9. Не «exactly-once»: доставка at-least-once, эффект однократный за счёт идемпотентного обработчика.
10. POST не становится идемпотентным методом (RFC 9110) — идемпотентна операция с ключом.
11. Replay — ответ на момент первого запроса, не текущее состояние.
12. Двойной тап: спасает, только если ключ создан до тапа. Одна фраза в норме.

## 5. Заблуждения зрителя
| место | думает | показываем |
|---|---|---|
| хук | «дважды нажал — заблокируем кнопку» / «вернул ошибку — не списал» | ответ рвётся после списания; итог неизвестен; повтор законен |
| норма | «ключ = номер заказа» | ключ на попытку оплаты |
| 1.1 | «проверим, был ли платёж» | платёж пишется после банка; check-then-act |
| 1.2 | «второй получил ошибку — дублей нет» | деньги ушли, «ошибка» → новая попытка → второе списание |
| 1.3 | «пусть второй ждёт на блокировке» | 409 и повтор позже: ждать на замке = держать транзакцию через банк |
| кейс 2 | «под упал — откатилось — чисто» | банк уже списал; `processing` навсегда, вечные 409 |
| 2.1 | «перехватим по сроку, как в 01» | перехват = второй вызов банка = второе списание |
| 2.2 | «проверим у себя» | у нас записи нет; знает только банк → тот же ключ банку |

## 8. Обложка и финал
- Title «Двойное списание». Tagline: «Как повторить оплату после обрыва связи и не списать деньги дважды» — честно для
  повтора того же запроса в окне хранения ключа.
- Outro: «Кто повторяет — шлёт тот же ключ, кто списывает — помнит ответ. И так по всей цепочке до банка.» / короче:
  «Повтор безопасен, когда ключ идёт по всей цепочке, а ответ на него помнят.» Не «ключ не даёт списать дважды».
- Отсылка к 01: «Почта: уже отправлено» → «тогда дубль погасил получатель по ключу; теперь получатель — мы».

## 9. Состав
1. Знакомство + норма (одно списание). 2. Хук (обрыв ответа). 3. Кейс 1 «Повтор оплаты: как списать один раз?» — 1.1
SELECT, 1.2 захват ключа + «ключ уже использован» → новый ключ, 1.3 ответ в строке ключа (`done` → replay, `processing` →
409). 4. Кейс 2 «Под упал после списания. Что ответить повтору?» — 2.1 `processing` навсегда, 2.2 lease → второе списание,
2.3 ⟲ ключ в банк. 5. Итог повтором кадров. Резать первым 2.1 (слить с 2.2).

В описание: 422, срок жизни и чистка, область ключа, какие ответы сохранять, `context.WithoutCancel`, сверка и вебхуки,
nginx, authorization/capture, RR и `ON CONFLICT`.
