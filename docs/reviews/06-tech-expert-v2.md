# Эпизод 06 — tech-expert, сверка смысла после learning-designer и tech-writer, 24.10

Взято всё.
- **Ошибка, кадр 31:** «SERIALIZABLE закрывает все пути разом» — неправда: путь, который сам не проверяет места
  (админка переносит заказ без подсчёта), сериализуем вместе с остальными и всё равно перегрузит курьера. Честно:
  счётчик — производные данные, их правят везде (и при отмене); на SERIALIZABLE хранить нечего — каждый путь сам
  пересчитывает заказы в своей транзакции.
- **Ошибка, код SERIALIZABLE:** ошибки count и INSERT игнорировались, а 40001 может прийти на любом запросе; тогда
  pgx на Commit вернёт ErrTxCommitRollback, а не 40001, и обёртка повтора его пропустит. Код проверяет err у каждого
  запроса; пометки «40001 с любого запроса» / «или на коммите». Окно кода 06 — 12 строк (`drawCode(…, rows)`).
- Кадр 13: RR сверяет строку, которую меняют или удаляют, — «после его снимка», а не «после начала транзакции».
- Кадры 19–20: направление зависимости («B посчитал без заказа A → B должен был идти раньше A»); «цикл» честен —
  для двух транзакций опасная структура SSI вырождается в цикл. Для описания: в общем случае Postgres ищет две
  rw-зависимости подряд, поэтому ловит каждый цикл и иногда прерывает без цикла (README-SSI).
- Кадр 21: судьбу B решает коммит A (B обречена), ошибку B получает на ближайшем операторе; «чаще на коммите» не
  подтверждено — «на любом запросе транзакции».
- Кадр 17: «в каком-то порядке»; кадр 23: «менял строку, которую уже поменял сосед»; кадр 29: «но и у этого способа
  есть цена».
- В описание: счётчик триггером; индекс под предикат (без него метка на всю таблицу и лишние 40001); READ ONLY
  DEFERRABLE для отчётов.
