# Эпизод 04 — tech-expert по черновику арки (22.10)

Вход: `docs/episodes/04-unique.md` (черновик арки). Всё ниже взято в сценарий v0.

## Ошибки (зритель запомнит неправду)
1. **Попытка 1 не 🟢 по памяти, если блокнот пода живёт весь день** — каждый под копит почти весь список (3 копии
   свитка). Решение: блокнот пустеет со сбросом копилки (видно в кадре); Аня на A и C в одном окне → 2. Голос не
   говорит «на одном поде было бы верно». 🔴 🟢 честно.
2. **Хук до номерка:** без cookie под не узнает Аню даже сам у себя. В хуке у Ани уже бирка `vid a81f` без
   объяснения; норма объясняет, откуда она.
3. **Хук и попытка 1 — один механизм:** попытку 1 сжать в один кадр «это и был хук» + лампы.
4. **«Влезает в память» неверно для Postgres:** список — таблица на диске; 16 Б × 10 млн = 160 МБ голыми, с
   заголовками и индексом ~0,7–1 ГБ. Цена — растёт с числом людей, на каждую ссылку и день; `count(*)` перебирает
   всё. Критерий — «**весит мало**»; голос «миллионы номерков, сотни мегабайт на один день»; «160 МБ» не называть.
5. **HLL не знает, кто новый:** новый Борис может не изменить ящик. `PFADD → 1` = «изменился регистр». Над
   HLL-подом нет «Новая!»; в кадре повтора Борис попадает в занятый ящик с меньшим столбиком. Голос: «HLL не помнит,
   кто был; он оценивает, сколько всех». Иначе зритель вынесет модель Bloom filter.
6. **Обложка против финала:** tagline «как их всё-таки объединить»; outro — «…храним не число, а маленький слепок,
   который умеет сливаться» (точный список тоже сливается, отличие HLL — вес).

## Решения по открытым
- **HLL в Postgres, расширение `hll` (citusdata/postgresql-hll)**; Redis до 02 не трогаем. Таблица
  `link_uniques(code, day, uniques hll)`; сброс пода — `UPDATE … SET uniques = uniques || $1` (`||` = `hll_union`,
  слияние в базе одним UPDATE); чтение `#uniques`; год — `SELECT #hll_union_agg(uniques) … WHERE day >= …`.
  **Нельзя:** под читает ящики, берёт максимум и пишет обратно — read-modify-write, lost update.
- Размеры: по умолчанию 2 048 ящиков ≈ 1,3 КБ, ≈ 2,3 %; log2m=14 — 16 384 ящика ≈ 10 КБ, ≈ 0,8 %. Голосом —
  «килобайты, ошибка около процента». «12 КБ» — цифра Redis, не называть.
- Копилка пода: 16 ящиков в памяти, раз в 5 с отдаёт в базу и обнуляет. **Хэш одинаков на всех подах** — тот же
  `vid` → те же биты на A и C → тот же ящик, max — Аня один раз. Показать.
- Бонус-рифма с 03: max идемпотентен — повтор сброса ящиков ничего не меняет (кликам ключ батча всё равно нужен).
- Малые числа: linear counting n ≈ m·ln(m/V): 1 → 1,03; 2 → 2,14; 3 → 3,3 («≈ 1/2/3»), если Аня и Борис в разных
  ящиках (подобрать `vid`). Реальный postgresql-hll на малых — EXPLICIT, точно (в описание).
- Монетка верна для одного ящика; один ящик может повезти — поэтому ящиков много и оценка их усредняет. Ошибка
  ≈ 1,04/√m: 26 % на 16, ≈ 0,8 % на 16 384 (Flajolet et al., 2007).

## Модель симуляции
- Хэш 32 бита: FNV-1a по `vid` + `fmix32` murmur3 (`Math.imul`). «Сумма кодов % 16» нельзя. `vid` Ани/Бориса
  подобрать офлайн.
- Старшие 4 бита — ящик; ρ = ведущие нули в оставшихся 28 битах + 1. На экране — нули, в формуле ρ.
- Слияние `M[j] = max`. Оценка `E = α·m²/Σ2^(−M[j])`, α₁₆ = 0,673; при `E ≤ 2,5m` и пустых ящиках — `m·ln(m/V)`.
- Кадр «≈ 10 000»: игрушка на 16 ящиках даёт что даёт (±26 %), seed не подгонять; рядом «настоящий HLL, 16 384
  ящика» — по тем же `vid` с p=14, посчитанное число без округления. Голос: «на шестнадцати ящиках ошибаемся на
  четверть; в настоящем — шестнадцать тысяч ящиков, килобайты и около процента».

## Ярлыки
Unique visitors (норма) · Non-additive measure (1.1) · Exact distinct count (1.2) · HyperLogLog (1.3) · HLL union
(кейс 2). Не использовать: Rollup, Unique users, Bloom filter, Probabilistic set, Exactly-once, Approximate set,
Mergeable sketch (можно голосом).

## В описание
- Ключ (`code`, `vid`); cookie `sho.rt` уходит с любой ссылкой. Без cookie — новый `vid` на клик, завышение;
  `hash(IP+UA)` слипает офисы. Safari ITP (bounce tracker, стирание через 7 дней), GDPR-согласие.
- Точный вариант: пачка `vid` — `INSERT … ON CONFLICT DO NOTHING RETURNING` + счётчик по вставленным.
- Партиционирование по `vid`: множества не пересекаются — уникальные складываются; цена — перебалансировка.
- HLL: Redis 16 384 регистра, 12 КБ, 0,81 %, PFADD/PFCOUNT/PFMERGE; postgresql-hll 2 048, 1,3 КБ, EXPLICIT/SPARSE;
  HLL++. Один хэш и seed везде, формат ящиков пода = базы (storage spec). Theta sketch (пересечение),
  `approx_count_distinct` (ClickHouse, BigQuery). Окно сброса не перешагивает полночь.
