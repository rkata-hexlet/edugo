Прогон модели по изменённым кадрам:
- Порядок строк в результате везде даёт `listing()` = `ORDER BY price, id` без удалённых. Это ровно то, что вернул бы запрос.
  Проверил 7, 9, 11, 19, 20, 23, 25, 27: состав и порядок страниц, скобки «отсчитал 5 / взял N» и номера 1–5 верны.
  В 9 «взял 4» тоже верно: после DELETE строк 9, и `LIMIT 5 OFFSET 5` возвращает 4.
- 14: счётчик «прочитано 3 000 / отдано 1 000», голос «две тысячи прочитать и выбросить, тысячу отдать». Сходится.
- 15: `OFFSET 1999000`, прочитано 2 000 000, сумма 2 001 000 000. Надпись «весь индекс» на последней странице буквально
  верна: 1 999 000 + 1 000 = все 2 000 000 записей. Подпись появляется только при `page > 3`, а в эпизоде это одна страница 2000.
  Тонкость в файл, не в кадр: при `SELECT *` это Index Scan, и каждая выброшенная запись читается ещё и из heap (Limit
  получает от сканирования целые строки). Голос «читает строку за строкой» это и говорит, так что «весь индекс» —
  преуменьшение, а не ложь. На такой глубине планировщик может выбрать и Seq Scan + Sort, но работа всё равно O(n).
- 29: `(created_at, id) > ($1, $2)` на btree `(created_at, id)` — row comparison действительно работает как условие индекса,
  то есть «сразу встаёт на закладку» верно. https://www.postgresql.org/docs/current/functions-comparisons.html#ROW-WISE-COMPARISON
- 30: «сто броней из пакетного импорта получили одно и то же время» — точно: `now()` / `DEFAULT now()` возвращает время
  начала транзакции, поэтому все строки одной транзакции получают одно значение. «Потеряется, как Лагуна» верно для
  строгого `>`. https://www.postgresql.org/docs/current/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT

## Ошибки

### О-1. Кадр 28: «Можно ли обойтись и без этого дубля? Только снимком…» — неверно, есть дешёвый путь
Этот дубль убирает обычная дедупликация по id на клиенте: экран не показывает карточку, id которой уже есть в ленте.
Так делают почти все бесконечные ленты, и на собеседовании это первый ответ на вопрос. Снимок нужен для другого: чтобы
выдача вообще не менялась под гостем. Вторая мелочь: «сохранить себе весь список» с подами не связано (список кладут в
общее хранилище). Дорог он тем, что это состояние на каждого гостя.
- Замена (голос 28 целиком): «Можно ли обойтись и без этого дубля? Проще всего на экране: не показывать карточку, которую
  гость уже видел, по её id. А чтобы выдача вовсе не менялась, пока гость листает, нужен снимок на всё листание: держать
  транзакцию открытой или сохранить весь список для каждого гостя. Это дорого. И гость будет видеть уже проданные номера и старые цены.»
- Минимальная правка, если добавлять фразу нельзя: «Можно ли, чтобы выдача вовсе не менялась? Только снимком на всё
  листание…» (дальше как сейчас). Вопрос тогда про снимок, а не про дубль, и неправды нет.

## Искажения метафоры

### М-1. Кадр 12: в SQL подсвечен `OFFSET 0`, а голос говорит о порядке и индексе
`sqlMark` для выгрузки подсвечивает OFFSET всегда, и на первой странице горит `OFFSET 0` амбером (цвет «отсчитал»), хотя
кадр про «в порядке времени создания и id… под этот порядок есть индекс… первая страница дешёвая». Подсветка показывает
не то, о чём голос. К тому же первая страница гостя написана без OFFSET, а первая страница выгрузки — с ним.
- Правка: в `exportPage` для `page === 1` писать SQL без OFFSET (как `SQL.offset` у гостя). В `sqlMark` для выгрузки без OFFSET
  подсвечивать `ORDER BY created_at, id`, по аналогии с кадром 3.

## Рекомендации

### Р-1. Кадр 3: id в `ORDER BY` на экране, но не в голосе (вопрос из журнала)
Смыслу это не мешает. В кадре 2 голос уже назвал колонку id, в 19 объясняет её роль, в 21 «сортировка была верной с самого
начала» опирается на SQL, который весь эпизод на экране. Подсветка всего `ORDER BY price, id` при голосе «по цене» не врёт:
порядок действительно такой. Одна оговорка для собеседования, в описание: без уникального добавочного ключа порядок
равных строк не определён, и OFFSET может давать дубли и пропуски даже на неизменной таблице. «Postgres returns an
unpredictable subset … unless ORDER BY constrains the order to be unique».
https://www.postgresql.org/docs/current/queries-limit.html
Если пользователь захочет посадить зерно раньше, хватит пяти слов в 3: «…отсортируй по цене, а при равной по id, и отдай
первые пять». Решать ему: кадр 3 переписан им сознательно.

### Р-2. Кадр 30: окна SQL нет, хотя голос объясняет пару
У кадра нет `action`, а `Director.shot` в начале каждого кадра очищает `w.sql`, поэтому флаг `sql: true` мёртвый, и окна на
снимке нет. В кадре 28 то же самое, но там SQL и не нужен. Для 30 полезно вернуть запрос выгрузки с подсветкой
`(created_at, id)`: голос говорит именно о том, зачем там id. Ничьи по времени в картинке нет совсем. Это допустимо, флажок
«09:12:05 | 880412» держит смысл, но на шлифовке можно дать подсказку (несколько засечек с одинаковым временем).

### Р-3. Кадры 29–30: строка табло «(price, id) >» горит зелёным «быстро» для выгрузки по `(created_at, id)`
Читается как «закладка-пара», и это допустимо. Если на табло найдётся место, подпись «пара» снимет вопрос, какой ключ имеется в виду.
