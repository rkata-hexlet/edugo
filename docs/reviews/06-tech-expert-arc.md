## Модель и наивный код
- `slots (id, window '18–20', cap 3)`, `orders (id, customer, slot_id → slots)`, индекс по `slot_id` подразумевается.
  В слоте 7 два заказа. `booked` появляется только в 2.3: «занято» здесь — подсчёт строк.
- Наивно (RR): `SELECT count(*) FROM orders WHERE slot_id = 7` + `SELECT cap FROM slots WHERE id = 7` → `if booked < cap
  { INSERT INTO orders … }` → Commit. Существующие строки никто не меняет — write skew честный. FK берёт `FOR KEY SHARE`
  на слот, KEY SHARE совместимы — никто не ждёт.

## SERIALIZABLE по шагам (наш таймлайн: оба читают, оба вставляют, A коммитит, B коммитит)
1. count(*) → SIRead-метка (index scan — страницы индекса с ключом 7; seq scan — вся таблица; на демо будет seq scan).
   Никого не блокирует.
2. INSERT A попадает в метку B → зависимость. Ошибки нет. 3. INSERT B попадает в метку A → кольцо. Ошибки нет.
4. COMMIT A: предкоммитная проверка видит кольцо, B помечен обречённым; A коммитится.
5. B получает 40001 на COMMIT: `could not serialize access due to read/write dependencies among transactions` (в 05 —
   `due to concurrent update`). Если A закоммитил до INSERT пода B — B падает на INSERT. Первый закоммитивший выигрывает.
   Голосом: «при записи или на коммите», в нашем таймлайне — «на коммите». Повтор B: новый снимок, 3 из 3 → «слот занят».
- Носитель: **пунктирная рамка-метка пода** вокруг заказов слота и пустого места под ними, не замок. Чужой INSERT в рамке —
  вспышка и нить-зависимость; две встречные — кольцо.

## Почему RR молчит
«REPEATABLE READ ругается, только когда транзакция меняет строку, которую после её снимка изменил кто-то другой, как
остаток кружки. А тут каждый вставил свою, новую строку. Общее у них только прочитанное „два из трёх“, а за прочитанным
REPEATABLE READ не следит.» Слово «фантом» в ролик не брать (в PG RR phantom read нет; нюанс — в описание).

## Цена SERIALIZABLE
Перестраховывается (ложные срабатывания) → повтор нужен для любой транзакции; работает, только если все пишущие тоже на
SERIALIZABLE. Не говорить «тормозит», «выполняет по очереди»: идут параллельно, эквивалентен результат.

## Счётчик в строке слота (2.3)
`UPDATE slots SET booked = booked + 1 WHERE id = 7 AND booked < cap` → `if RowsAffected() == 1 { INSERT }`. **На READ
COMMITTED** — голос обязан сказать «вернёмся на уровень по умолчанию». B ждёт (видимая разница с 2.1), после COMMIT A
перепроверка 3 < 3 → 0 строк → «слот занят», без повтора. На RR — 40001 и повтор (одна фраза/описание).
Цена: `booked` — денормализованная копия подсчёта (завести, уменьшать при отмене), все заказы слота — к одной горячей
строке. FOR UPDATE на слоте — одной фразой (оговорка «только на RC» — в описание).

## Где картинка соврёт
Замок на SIRead; ожидание в 2.2; молния на INSERT при незакоммиченном A; слон, считающий места (он видит только «ты
прочитал то, что другой изменил»; реплика ≤ 37 знаков, «Читали то, что другой поменял. Заново!»); 40001 ≠ «слот занят»
(это пишет наш код после повтора); «конфликт» в двух смыслах — развести голосом; отсылка к 05 подчёркивает «оба писали в
одну строку stock».

## В описание
Гранулярность меток, индекс по slot_id; 40001 и на чтении; обратный порядок коммитов; откат A — B проходит; FOR UPDATE
только на RC (на RR снимок до ожидания замка); `pg_advisory_xact_lock`; `EXCLUDE USING gist`; `CHECK (booked <= cap)`;
Oracle SERIALIZABLE = snapshot isolation, MySQL SERIALIZABLE — блокирующие чтения; `SERIALIZABLE READ ONLY DEFERRABLE`;
повтор в Go (40001, лимит, backoff); «phantoms causing write skew» (DDIA).
