## 1. Модель
- `products`: 3 «Чайник» stock 10; 7 «Кружка» stock 10 (кружку завезли — рифма со стикером «скоро завезём» из 05).
  Остаток большой: товара хватает обоим, 40P01 нельзя спутать с «нет в наличии». `orders`.
- Корзины: Аня — кружка, чайник (7, 3); Борис — чайник, кружка (3, 7). Количество по 1 — запрос дословно из 05.
- Наивный код (READ COMMITTED, порядок — как положил покупатель):
  ```go
  tx, err := pool.Begin(ctx)
  if err != nil { return err }
  defer tx.Rollback(ctx)
  for _, it := range cart.Items {
      tag, err := tx.Exec(ctx,
          `UPDATE products SET stock = stock - 1 WHERE id = $1 AND stock > 0`, it.ProductID)
      if err != nil { return err }
      if tag.RowsAffected() == 0 { return ErrOutOfStock }
  }
  if _, err := tx.Exec(ctx, `INSERT INTO orders …`); err != nil { return err }
  return tx.Commit(ctx)
  ```
  Беда: `for` идёт по корзине в её порядке, а каждая запись держит строку до коммита [LOCK 13.3.2].

Таймлайн (жертва — Борис, «Борис всегда второй»):
1. A: `UPDATE id=7` — кружка за A. B: `UPDATE id=3` — чайник за B. Оба сразу, строки разные.
2. B: `UPDATE id=7` — **B ждёт A**, и ждёт конца транзакции A (COMMIT/ROLLBACK), а не «пока A закончит с кружкой».
   Отсчёт `deadlock_timeout` у B пошёл.
3. A: `UPDATE id=3` — **A ждёт B**. Цикл замкнулся; сразу его никто не ищет: проверка дорогая, база выжидает
   `deadlock_timeout`, 1 с по умолчанию [DT].
4. Через ~1 с у B срабатывает таймер; проверку графа «кто кого ждёт» запускает серверный процесс Postgres соединения B
   (не под на Go), находит цикл и прерывает **свою** транзакцию [LMGR: «the first one to do so will be the victim»].
   На практике жертва — кто начал ждать первым. Документация: какую прервут, «difficult to predict» [LOCK 13.3.4].
   Цены/возраста, как SQL Server или InnoDB, PG не учитывает.
5. B получает ошибку на ждущем `UPDATE id=7` (не на COMMIT): `ERROR: deadlock detected (SQLSTATE 40P01)`,
   `DETAIL: Process … waits for ShareLock on transaction …; blocked by process …`. Откатывается **вся** транзакция B
   (чайник возвращён, замок снят); дальше 25P02 до ROLLBACK — сделает `defer`. Наш код возвращает err: Борис видит
   «Не удалось оформить заказ», хотя товара полно.
6. A дождался: на RC `stock > 0` перепроверяется на свежей версии (как в 05), A списывает чайник, коммитит. Аня получает
   ответ **на ~1 с позже** и не знает, что что-то было.

40P01 и 40001: общее — класс 40, транзакция отменена, повторяет **наш код** с BEGIN [RETRY]. 40001 — конфликт данных,
только RR/SER, после повтора ответ может измениться. 40P01 — данные ни при чём, двое ждут друг друга; любой уровень,
включая RC; приходит на ждущем запросе после ≥ 1 с; повтор почти всегда проходит с тем же ответом. 40P01 убирается
порядком в коде, 40001 на SERIALIZABLE — штатная цена уровня.

## 2. Арка попыток
Табло: **«оба заказа приняты»** / **«без повтора»**. «Без ожидания» не брать: при сортировке B тоже коротко ждёт.

| попытка | в ролик? | приняты / без повтора |
|---|---|---|
| наивный цикл (хук) | да | красный / пусто |
| «поднимем изоляцию» (SERIALIZABLE) | одной фразой (рекомендую) | красный — замки строк те же на любом уровне |
| повтор на 40P01 | да | зелёный / жёлтый |
| сортировка по id в Go | да, главное | зелёный / зелёный |
| `SELECT … WHERE id = ANY($1) ORDER BY id FOR UPDATE` | фразой (⟲ Иначе) или описание | зелёный / зелёный |
| один `UPDATE … WHERE id = ANY($1)` | возражение умного зрителя, одна фраза | порядок не гарантирован |
| `lock_timeout` / `statement_timeout` / ctx | описание | красный |
| NOWAIT / SKIP LOCKED | описание | не к месту |

- Повтор: оба теряют ≥ 1 с, жертва работает дважды; на распродаже deadlock повторяется, хвост задержек. Снижать
  `deadlock_timeout` — платить проверкой за каждое ожидание.
- Сортировка: `slices.SortFunc(items, func(a, b Item) int { return cmp.Compare(a.ProductID, b.ProductID) })`. Оба
  идут 3 → 7; второй ждёт на **первой** строке, ничего не держа — цикла нет. После COMMIT A у B перепроверка
  `stock > 0`, B проходит (механизм 05). Рекомендация документации «consistent order» [LOCK 13.3.4]. **Без повтора
  только на READ COMMITTED**: на RR/SER B после ожидания получит 40001. Голос: «мы на READ COMMITTED, как в 05».
- `FOR UPDATE ORDER BY`: порядок задаёт база (ORDER BY до запирания) [SEL]; когда строки находятся запросом. Цена —
  лишний запрос.
- Один `UPDATE … = ANY`: порядок запирания зависит от плана (index scan — по ключу, seq scan — физический), у UPDATE
  в PG нет ORDER BY. Голосом: «один запрос не обещает, в каком порядке запрёт строки».
- Таймауты меняют 40P01 на 55P03/57014 и рвут честные очереди; `lock_timeout < deadlock_timeout` — детектор не успеет.
- SKIP LOCKED пропустит товар (инструмент очереди 01); NOWAIT — ошибка на любом касании популярного товара.

Когда что: транзакция запирает несколько строк — всегда в одном порядке (сортировка или `FOR UPDATE ORDER BY`), **во
всех путях** (оформление, отмена, админка, склад — рифма с 06 «поправлять везде»); повтор на 40P01 — страховка
(триггеры, FK, чужой сервис); транзакции короткие.

## 3. Заблуждения по кадрам-поворотам
- Знакомство: «UPDATE отпускает строку, как только выполнился» — ядро темы. Голос до хука: «строка заперта до коммита».
- Перед хуком: «атомарный UPDATE спас», «товара полно». «Казалось бы, хватает обоим, а столкнутся — один подождёт, как в 05».
- Взаимное ожидание: «зависнут навсегда» / «Postgres сразу видит». Нить «кто уступит?» + секундомер; носитель
  `deadlock_timeout` — у слона/стрелки ожидания, **не над подом**. «Не будет ждать вечно, но и цикл ищет не сразу».
- Ошибка: не «кончился товар», не баг PG; «база сама повторит» — нет, повторяет наш код; жертва — «заранее не угадать».
- Перед попытками: «это уровень изоляции, в 06 спас SERIALIZABLE» — «замки строк одинаковы на любом уровне»;
  главная ловушка зрителя 06, в ролике обязательно.
- «Deadlock в Go, нужен мьютекс»: горутины ждут сеть; `all goroutines are asleep` — другое; поды — разные процессы.
  Одной фразой: «цикл ожидания не в Go, а в базе».
- Повтор: цена — секунда у обоих и двойная работа; перед сортировкой сказать, чем повтор не устроил.
- Сортировка: «никто не ждёт» — ждёт, но в очереди, ничего не держа; порядок общий для всех путей.
- Возражения умного зрителя: «почему не одним UPDATE?» (рекомендую); «почему целую секунду?».

## 4. Рифма и отсылка
- Честно: спаситель из 05 сам и запирает. В 05 B ждал A — это спасло; тут каждый ждёт другого — это губит. Отсылка
  сценой 05 «B ждёт коммита A». «Любая запись держит строку до коммита, и наш UPDATE тоже». Натяжка — «атомарный
  UPDATE виноват»: read-modify-write и FOR UPDATE запирают так же.
- 06, кадр 29 «цена: строка заперта до коммита» → две такие строки — уже не очередь, а кольцо. «Поправлять везде» →
  «порядок везде».
- Опасная рифма — цикл SSI 06 (там никто не ждёт). Развести голосом («теперь каждый действительно стоит и ждёт») и
  графикой (сплошные стрелки к замкам, не пунктирные дуги), иначе 40001 и 40P01 склеятся.
- Слот в той же транзакции (products → slots / slots → products) — только в описание.

## 5. Ярлыки, обложка, outro
- `Deadlock` (хук); `Deadlock detection` — если нужен отдельный; `Retry on deadlock`; `Lock ordering`. Не брать
  `Deadlock avoidance` (алгоритм банкира) и `Wait-for graph` в ярлыке.
- Обложка: «Двое ждут друг друга» / «Товара хватает обоим, а заказ Бориса падает с ошибкой. Как не дать заказам
  запереть друг друга?» Не обещать «никогда не получить deadlock».
- Outro: «Транзакция держит запертые строки до коммита, поэтому, если запираете несколько, делайте это везде в одном
  порядке, например по id, а повтор на 40P01 оставьте страховкой».

## 6. В описание
Кто запускает проверку и почему жертва — первый ждущий; soft deadlock (перестановка очереди); «ShareLock on
transaction» — замок строки в xmax; `log_lock_waits`, `pg_locks`, `pg_blocking_pids()`; жертва по стоимости — InnoDB,
SQL Server; `lock_timeout` 55P03, `statement_timeout`/ctx 57014; NOWAIT/SKIP LOCKED; `UPDATE … = ANY`; `FOR UPDATE
ORDER BY`; транзакция на позицию — заказ наполовину; `pg_advisory_xact_lock` — гуськом; повтор в Go (`errors.As`,
40001/40P01, лимит, backoff с jitter, внешние эффекты вне транзакции); сортировка на RR/SER — 40001; порядок между
таблицами и путями; FK: UPDATE ключа — FOR UPDATE против FOR KEY SHARE, UPDATE stock — FOR NO KEY UPDATE; FOR SHARE,
потом UPDATE — deadlock на одной строке; распределённый deadlock (мьютекс/пул + БД, две базы) детектор не видит.
