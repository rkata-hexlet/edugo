## Мерило: что делает тему хорошим уровнем
Четыре признака. Нужны все:
1. **Решение — сочетание 2–4 кирпичей, а не один.** Если «поставь X» — выбор очевиден (ADR-0007 это и говорит про 01).
2. **Лекарство само ломает.** Очевидный кирпич создаёт новую беду, которую чинит другой кирпич (ретрай → дубль → ключ).
3. **Две победы с разной ценой**, измеримой тремя числами табло (как 112/145 в уровне 1).
4. **Поломка рисуется как состояние схемы** (столбик, очередь, две карточки), а не как невидимое свойство данных.
Тема, у которой нет признака 2 или 4, остаётся роликом (или поводом для викторины в канале).

## Вопрос 1. Кандидаты с настоящей ловушкой и неочевидным выбором

Оценка: ★★★ — делать уровнем в первую очередь; ★★ — можно, но нужна работа; ★ — лучше роликом/викториной.

| тема | оценка | цель уровня | беды | ловушка «починил — сломал» | выбор с ценой |
|---|---|---|---|---|---|
| **Rate limit / виртуальная очередь** (из «запаса» мира отеля) | ★★★ | пережить распродажу номеров, не уронив поставщика и не отказав всем | всплеск 10× за секунду; один клиент-бот; потом всплеск после «паузы» | лимит по IP режет честных за NAT; лимит «на под» при N подах = N× лимит; жёсткий отказ → клиенты ретраят волной (retry storm из уровня 1 возвращается) | «429 + Retry-After» (дёшево, злит) против виртуальной очереди (честно, держит состояние, добавляет задержку) |
| **Poison message / очередь + DLQ** | ★★★ | рассылка не должна вставать из-за одного письма | битое сообщение; временный сбой, который проходит со второй попытки | ретрай «без конца» вешает партицию (лечит лимит попыток); лимит попыток в 1 теряет письма при кратком сбое (лечит backoff); DLQ без разбора — тихая потеря | лимит 3 попытки + DLQ против «бесконечный ретрай + алерт»: задержка здорового потока против потери |
| **Деньги / копейки** | ★★ | сумма сходится после скидки и возврата | возврат одной позиции; повторная выгрузка | округление «в каждой позиции» → не сходится; «округлим итог» → позиции не сходятся с чеком | распределение остатка против хранения разбивки; выбор есть, но суше картинки (числа, не поток) |
| **Время / напоминание в 10:00** | ★★ | гость получает напоминание в правильный местный день | отель в другом поясе; переход на летнее время; полночь UTC — все рассылки разом | «храним UTC» чинит переход, ломает «дату заезда» (она дата, не момент); крон по местному чинит это и даёт дубль/пропуск при переходе | мало кирпичей-механизмов, больше выбор типа данных: хуже как «сборка системы» |
| **Миграция без простоя** | ★★ | добавить поле днём, не остановив брони | долгий отчёт держит замок; backfill на 50 млн строк | `ALTER` ждёт замок и за ним встаёт вся очередь (лечит `lock_timeout`); `lock_timeout` без повтора — миграция не применилась; backfill одним UPDATE — длинная транзакция, лаг реплики | `lock_timeout`+retry, пачки, `CONCURRENTLY`; цена — число релизов и время выкатки. Шаги — последовательность, а не палитра; уровень надо строить как «порядок шагов» |
| **Fan-out ленты** | ★★ | лента обычных людей мгновенная, звезда не кладёт очередь | пост звезды; пользователь на 2000 подписках | «раскладываем всем» (лечит чтение) ломается на звезде; «собираем при чтении» ломается на подписанных на многих; гибрид по порогу — порог и есть решение | запись против чтения против гибрида; хорошая развилка и хорошая картинка. Ловушка слабее: больше «выбор стратегии», чем «лекарство ломает» |
| **Деплой без 502 / пробы** | ★★★ | выкатить новую версию без ошибок гостям | SIGTERM посреди брони; база задумалась | readiness без дренажа — запросы идут умирающему; liveness с проверкой базы → k8s перезапустил все поды разом (классическая ловушка «починил — убил») | «пробы+дренаж» против «blue/green»: число подов и время выката |
| **Poison/outbox** (outbox в запасе) | ★★ | событие «оплачено» уходит ровно один раз | падение между записью и отправкой | «пошлём после коммита» теряет; «до коммита» шлёт то, чего нет; outbox чинит, но даёт дубли → нужен ключ у консьюмера | хорошая ловушка, но пересекается с 08/идемпотентностью: часть зрителей скажет «было» |
| **Мультитенантность / RLS** | ★ | админ не видит чужой отель | забыт `WHERE hotel_id`; `SET` в пуле | ловушка сильная (протекает в чужой запрос), но «беда» — невидимая утечка данных: картинка = «чужие карточки у меня» без динамики |
| **Идентификаторы** | ★ | номер брони не выдаёт продажи | перебор | выбор типа ключа, нет механизма и потока: ролик/викторина |
| **152-ФЗ / crypto-shredding** | ★ | удалённые данные недоступны везде | бэкап, лог, Kafka | выбор «архитектура хранения», беда не имеет скорости. Только ролик |
| **Ротация секретов** | ★ | сменить пароль без падения | все поды падают разом | есть сильная ловушка, но решение — один приём (два активных секрета); выбора нет → только ролик |
| **Реплика — не бэкап** | ★ | восстановиться после DELETE | DELETE без WHERE | решение одно (PITR); викторина лучше уровня |
| **Чат: pub/sub между подами + переподключение** | ★★ | сообщение доходит, деплой не кладёт сервис | деплой рвёт миллион соединений | jitter переподключения — это уровень 1 в другой обёртке; лучше сочетать с «деплой» |
| **Статус «онлайн»** | ★★ | статус не врёт и не спамит друзей | вкладка закрыта; метро мигает | heartbeat+TTL → мигание → гашение с задержкой; хорошо рисуется, мало кирпичей (2–3) — уровень «средний» |
| **Шардирование `hash % N`** | ★ | добавить сервер без переезда 75% данных | рост | выбор «логические шарды / consistent hashing»: оба верные, разница слабо ощутима в табло; симулятор врёт на «кэш разом промахивается». Ролик |

Что выбрать первым после отеля-ядра (11–14): **rate limit + виртуальная очередь**, **poison message + DLQ**,
**деплой + пробы**. У всех трёх есть поток во времени, ловушка «лекарство ломает», выбор с ценой, они используют
кирпичи уровня 1 (backoff, breaker, ретрай), то есть **переиспользуют палитру** — а новый кирпич ровно один.

### Что в этих трёх хорошо работает «ага» для мидла
- **Rate limit:** игрок ставит лимит, чтобы защитить поставщика, а клиенты, получившие 429, ретраят без backoff и
  возвращают волну. Это не пересказ уровня 1, а его продолжение: игрок сам узнаёт, что «защита от retry storm без
  backoff у клиента не работает».
- **Poison/DLQ:** ловушка «лимит попыток = 1» теряет письма при коротком сбое. Мидл обычно знает про DLQ, но не
  про цену слишком раннего отказа.
- **Деплой:** игрок добавляет проверку базы в liveness, потому что «живой под должен видеть базу», и получает
  одновременный перезапуск всех подов. Мидл узнаёт «у нас так было».

## Вопрос 2. «Отель целиком» из кирпичей 10–14, до новых эпизодов

**Важно:** из доступных мне файлов я не вижу кирпичей 11–14 как кода. По `state.md` и `ideas.md` гипотеза такая:
- 10: таймаут, вызов вне транзакции, ретрай, ключ, backoff+jitter, breaker (реализован, уровень 1).
- 11: реплика + отставание (read-your-writes): кирпичи «читать с реплики», «читать с мастера после записи» (sticky по
  сессии / по LSN).
- 12: сага: шаги + компенсации; кирпичи «компенсация», «шаг сохраняется в журнале».
- 13: keyset-пагинация: кирпич «курсор» (мало связан с остальным).
- 14: feature flags: «флаг», «постепенный выкат», «expand/contract».

Рекомендация по составу:

1. **Не делать отдельный уровень на каждый из 11–14.** Уровень на один эпизод слабый (ADR говорит это про 01).
   Исключения: сага (12) — естественно сочетается с ключом и ретраем уровня 1; реплика (11) — с кэшем.
2. **Уровень 2 (после 11–12): «Бронь с оплатой».** Палитра: ключ, ретрай, таймаут, breaker (из уровня 1, **уже
   включены и показаны**, игрок их знает) + новое: **сага/компенсация**. Беда: оплата прошла, поставщик отказал,
   надо вернуть деньги; компенсация сама упала. Ловушка: компенсация без ключа → двойной возврат; сага без
   журнала → после падения пода «подвисшая» бронь. Это сочетание ровно того, чем ценен конструктор.
3. **Уровень 3 (после 11 или 12): «Гость видит свою бронь».** Реплика + кирпич «читать с мастера после записи» +
   (если есть) кэш. Беда: бронь создана, гость обновил страницу — «брони нет» (отставание реплики). Ловушка: всё читать с
   мастера кладёт мастер в пик (противоположная цена); «читать с реплики по сессии» не работает при смене пода. Два
   решения с разной ценой (нагрузка на мастера против задержка).
4. **Финал «Отель целиком»:** одна схема, три беды подряд (медленный поставщик → оплата с откатом → отставание
   реплики) **плюс новая беда, которой ни один предыдущий уровень не называл** (например, деплой посреди брони). Игрок
   собирает схему сам из 8–10 кирпичей и должен **выбрать, чего не ставить**: финал оценивает не только победу, но и
   лишние кирпичи. Правило финала: **ни одной подсказки, ни одного «Намёка», пустая схема**.
5. Keyset (13) и флаги (14) не делать уровнями до отеля-целиком: keyset — «одна правильная форма запроса», выбора
   нет; флаги — процесс выкатки, не схема. Использовать как **кирпичи финала** (кирпич «флаг»: включить новое
   поведение процентами; ловушка — флаг включён, а миграция не накатилась).

Если этих кирпичей в кодовой базе окажется меньше — не наращивать финал, а сократить: три беды достаточно.

## Вопрос 3. Кривая сложности для 15+

Исходные данные: уровень 1 — 6 кирпичей, 2 беды, четыре ловушки, и это уже предел для телефона (экран 390×844,
сетка 2×3, «Запуск» на 805 px). Показа посторонним ещё не было, поэтому цифры ниже — гипотеза до отзывов.

| уровень | новых кирпичей | кирпичей в палитре | бед | подсказки |
|---|---|---|---|---|
| 1 (есть) | 6 (но все из одного эпизода) | 6 | 2 | пояснение при касании; «Намёк» нет |
| 2 | 1 (сага/компенсация) | 6–7 (старые не обязательно все; половина лишних) | 2 | пояснение, **без Намёка** |
| 3 | 1 | 6–7 | 2 | то же |
| финал отеля | 0–1 | 8–10 (**но экран держит ≤ 8: см. ниже**) | 3 | **никаких** |
| 15+ (новый мир) | 1–2 | 5–7 | 2 | первые 1–2 уровня мира: «Намёк» подсвечивает переключатель, не называет кирпич |

Правила:
- **Один новый кирпич на уровень**, старые — как «известный инструмент». Исключение: первый уровень нового мира
  может ввести два, если они парные (лимит + очередь).
- **Подсказки ломаем на уровне 2, а не 4.** Уровень 1 уже без Намёка в MVP, то есть подсказка-вывод есть только
  в пояснении. Пока уровней мало, не копить «подсказочные» уровни: игрок, перешедший на второй уровень, уже понимает
  формат «собрал → запустил → стоп-кадр».
- **Палитра на экране ≤ 8 переключателей** (сетка 2×4). Больше — прокрутка, а в портрете это конец «цикла в два
  касания». Если в финале нужно больше, объединять в группы: «защита вызова» = таймаут+ретрай+breaker как один
  переключатель с режимами — но тогда теряется выбор. Лучше отбирать, какие кирпичи доступны на уровне, а не вешать
  всё сразу.
- **Бед на уровне ≤ 2–3**: каждая беда — это ещё одна фаза прогона и ещё одна строка в карточке провала. Три беды
  только в финале.
- **Новый мир:** не ставить ловушку уровня 1 (ретрай без ключа) сразу. Первый уровень нового мира должен быть
  *легче* последнего уровня предыдущего: мир новый, интерфейс тот же, кирпичи частично старые, но значения иные.
- **Решений ≥ 2 с разным счётом на каждом уровне.** Если модель даёт одно решение — уровень выкинуть или
  переделать. Проверять тестом «перебор всех подмножеств» (уже есть для уровня 1).

## Вопрос 4. Какие темы остаются только роликом

Из таблицы: секреты, 152-ФЗ/crypto-shredding, идентификаторы, бэкап, шардирование, мультитенантность/RLS, фото через
под, keyset (как отдельный уровень).

Причины, по которым *уровень* не получается:
- **Нет потока во времени.** Уровень оживает, когда на экране нарастает беда (столбики, очередь). Ротация секретов —
  момент (все поды упали); 152-ФЗ — состояние хранилищ; ID — свойство формата. Нечему «прогоняться».
- **Решение — один приём.** Секреты: «два активных секрета». Бэкап: PITR. Выбора нет, значит, нет сравнения на табло.
- **Невидимая беда.** Утечка в RLS не имеет стоп-кадра, которым игрок сам бы это понял (он видит просто чужие данные,
  но не механизм).
- **Симулятор врёт.** Шардирование: «кэш разом промахивается», оценка 75% — оба нужны с честными цифрами; в
  симулятор это тащить дорого.
- **Фото через под:** картинка суха, а решение (presigned URL) — один шаг. Годится как **кирпич «загрузка мимо
  пода»** в уровне про нагрузку, но не как самостоятельный уровень.

Для канала это значит: их темы — **ролик + викторина + шпаргалка** (три формата A, C, D у channel-strategist).
Заменять на уровень не пытаться: это растянет конструктор там, где у него нет силы.

Промежуточные: время, деньги — хороши как **викторина-калькулятор** («сойдётся ли?»), не как конструктор.

## Вопрос 5. Уровни между эпизодами (закрыть «недели без эпизода»)

ADR-0007: уровни по кирпичам 01–09 — «позже, если конструктор приживётся». Моя оценка:

- **Пока конструктор не проверен на 3–5 посторонних — не делать ни одного.** Каждый уровень на старом кирпиче —
  сборка новой модели мира (сейчас кирпичи 01–09 живут как отдельные симуляции, общая модель — только отель).
- **Кандидаты в порядке пользы**, если решат делать:
  1. **«Двойное списание в отеле» (08 идемпотентность + 06 write skew/блокировка):** кирпичи ключ + блокировка строки
     + транзакция; ловушка: блокировка чинит двойное списание, но даёт очередь (deadlock → 07). Уже есть ключ в уровне 1,
     новое — блокировка строки.
  2. **«Остатки по ночам» (03 горячая строка + 07 deadlock):** порядок блокировок; ловушка — «упорядочить» чинит,
     «увеличить таймаут» — нет. Выбор: блокировка против оптимистичной версии.
  3. **«Кэш цены» (02 + 11):** кэш и инвалидация. Слабее: выбор TTL — это параметр, а в уровне 1 принцип «брать или
     нет», без параметров.
- **Между эпизодами лучше публиковать не новые уровни, а вариации одного:** тот же уровень 1 с другим составом бед
  («добавь двойной клик гостя», «поставщик отвечает быстро, но с ошибками 500»). Стоимость в модели — один флаг
  беды, в канале — новый повод вернуться. Из разбора stage5 уже есть пропуски на следующие уровни: двойной клик
  гостя, outbox вместо отказа, bulkhead, breaker на каждом поде. **Первое, что нужно, — «двойной клик» (малая
  стоимость, ловушка рядом с ключом) и «bulkhead» (альтернатива кирпичу «вне транзакции» — другая победа с другим
  счётом).**
- **Недели без эпизода закрывать викторинами и разбором решений игроков** (какие наборы кирпичей люди выбирали;
  какой стоп-кадр видели чаще всего) — это дешёвый контент из уже работающего уровня.

## Вопрос 6. Что считать «прохождением», как телефон меняет набор

**Прохождение** (для метрики) — три уровня, считать отдельно:
1. **Открыл** (зашёл) — воронка из поста.
2. **Запустил и увидел хотя бы один стоп-кадр** — показатель, что понял механику «собрал → запустил». Если
   много «открыл» и мало «запустил» — проблема в первом экране (цель за 10 секунд).
3. **Победил** (любое из решений). Дополнительно **попыток до победы** (медиана), **набор победы** (T O B K или все
   шесть) и **число кирпичей** — по ним видно, нашёл ли игрок экономное решение.
Не считать «лучшее решение»: в уровне 1 победы засчитаны одинаково (решение пользователя), «лучшее» зависит от
вкуса. Но *показывать* в канале распределение («60% поставили ретрай без ключа и получили дубль») — сильный контент.
Ориентир успеха этапа 2 из стратегии (≥ 30% ответивших на викторину открыли уровень) мерить как «открыл», а победу —
отдельно; цель по победе на старте — не выше 40–50% открывших (уровень не должен быть слишком лёгким).

**Телефон в портрете:**
- Сейчас сетка 2×3 + карточка провала + «Запуск» на 805 px из 844. Свободного места нет. Значит, **8 переключателей —
  потолок** (2×4), и «Запуск» уедет ниже 830 px. Практически палитра на уровне — **6–7**.
- Названия длиннее ячейки не влезают (уже случилось: «Вызов вне транзакции», «Ключ идемпотентности»). Для новых
  кирпичей — **имя ≤ 2 коротких слов**, пояснение по касанию.
- Один уровень = одна схема на экране без прокрутки; нельзя добавлять вторую схему «рядом» (финал отеля).
  Финал решать **сменой слоя**: схема гостя/платежа/чтения как три «вкладки» одной системы, но переключатели одни и те
  же. Это новая UI-механика, её нужно проверить на показе отдельно.
- Текст «почему» — главный потребитель высоты. Каждая новая беда добавляет строку, поэтому лимит «почему» ≤ 2 строк
  на телефоне.
- Касание вместо перетаскивания — оставить (уже так).

## Что важно для первого уровня после эпизода 10 с точки зрения канала

Первое впечатление идёт не от конструктора, а от **поста, который к нему ведёт**. Требования:

1. **Цель за 10 секунд с самого верха экрана на телефоне.** Сейчас шапка с целью показывается «только до первого
   запуска» — хорошо. Но человек пришёл из поста «собери сам». Первая строка уровня должна повторять фразу из поста
   дословно, чтобы не было ощущения «я не туда попал». Фраза-кандидат: «Гость жмёт "Забронировать", поставщик зависает.
   Спаси бронь и поиск».
2. **Первый «Запуск» без единого касания должен проваливаться и показывать полный стоп-кадр** (пустая схема → пул
   10/10 красным). Это лучший хук: игрок видит, что «система живая и ломается», до того как что-то понял. Не прятать
   этот провал за кнопкой «сначала собери». Для канала это и скриншот поста.
3. **Путь от поста до «Запуск» ≤ 2 касаний:** пост → ссылка → экран с целью → «Запуск». Без заставки, регистрации,
   имён, туториала. Telegram Mini App открывается по кнопке: имя игрока из Telegram, но никакого ввода.
4. **Постороннему из канала ролик 10 может быть ещё не знаком** (уровень выходит *после* 10, но канал читают не
   только зрители). Ссылка на ролик — после первого провала, не до. «Провал ведёт в ролик» — по ADR, а в
   level-01.md ссылку убрали («эта инфа не нужна»). Решение: **в стоп-кадре без ссылки, в посте-ответе (C) — со
   ссылкой на минуту**. Игрок не отвлекается, а канал получает второй заход.
5. **Победа должна легко превращаться в пост.** Экран победы: табло из трёх чисел + «поставили K и R, вышло 145 броней,
   257 запросов». Нужна кнопка «Поделиться» (текст: «Прошёл уровень набором из N кирпичей; а сможешь за 4?»). Сейчас
   такого нет; это самая дешёвая часть роста канала. Если делать *одну* правку для канала — эту.
6. **Две победы с разной ценой — и канал сам должен подсказать, что решение не одно.** Фраза в посте: «Есть как
   минимум два рабочих набора. Сколько кирпичей хватит тебе?» (экономное решение T O B K — 4 кирпича, полное — 6).
   Без этого 90% остановятся на первой победе.
7. **Телефон — единственный реальный экран канала.** Проверять на нескольких размерах: 360×640 (старые Android) и
   390×844. На 360×640 «Запуск» сейчас вряд ли виден без прокрутки. Минимум: «Запуск» закреплён внизу, а не следует
   за контентом.
8. **Отложенная нагрузка:** состояние в Mini App живёт на устройстве, поэтому «прохождение» в метрике надо считать
   на стороне страницы (пинг при победе без личных данных). Решить до показа на канал.
9. **Первый показ посторонним — три разных человека:** мидл-бэкендер (знает слова), джун (знает не все), не
   бэкендер (проверка «цель за 10 секунд»). План наблюдений — в разборах stage5.
10. **Тизер на неделе 4 скриншотом (решение автора №5) — только стоп-кадр провала.** Он самодостаточен и интригует;
   кадр победы не показывать, чтобы не отдавать решение.

## Замечания к самому плану канала (попутно)

- Этап 2 («уровень после 10», нед. 9–12): метрика «≥30% ответивших на викторину открыли уровень» плохо измерима —
  Telegram не даёт связать ответ на опрос и переход. Заменить на «переходов по ссылке уровня / просмотров поста».
- Таблица этапов ставит уровни 11, 12, 14 на недели 10–13, но на данный момент **нет ни одного описанного уровня,
  кроме первого**. Строка «+ уровень 11» в календаре обещает то, чего нет. Либо вынести в «возможно», либо начать
  проектировать уровни 2–3 по правилу ADR «сценарий сразу с уровнем» ещё для 11 и 12 (они не вышли, сценарии
  утверждены → досочинить можно, пока дубли не записаны).
- Нагрузка автора: 1–1,5 ч в неделю на публикации помимо эпизода и **ещё** конструктор. ADR сам называет конфликт; в
  плане его пока нет в рисках. Разумно *сначала* пустить посторонних на уровень 1 (нед. 4), а решение «делать
  уровни 2–3» принять после, как точку этапа 2.

## Вопросы к tech-expert
1. Rate limit: честно ли в симуляции показывать лимит «на под» против общего (токен-бакет в Redis) — и как
   моделировать виртуальную очередь без вранья о гарантиях порядка?
2. Poison message: что реально делает консьюмер Kafka / RabbitMQ / SQS при бесконечном ретрае одного сообщения
   (блокировка партиции — у Kafka, возврат в очередь — у SQS)? Модель должна выбрать одну из двух честно.
3. Liveness с проверкой базы: подтверждение, что k8s перезапускает все поды одновременно (а не по очереди) и как
   это объяснять без вранья (зависит от `failureThreshold` и `periodSeconds`).
4. Сага: что происходит с компенсацией, которая сама упала (бесконечный ретрай? человек?) — нужно для беды «компенсация
   сломалась».
5. Для уровня 3 (реплика): как честно показать «читать с мастера после записи» (sticky по сессии / по LSN / по таймеру) без
   превращения в три кирпича.
6. Правдивость «выбор по табло»: 112 против 145 броней — число зависит от порога breaker (16 из 20, подстройка
   под уровень). Не выучит ли игрок, что breaker всегда даёт меньше броней? Оговорка про порог в табло.
7. Финал отеля: можно ли честно показать три беды в одной ленте времени, не получив сочетаний, которые модель
   «не предусмотрела» (ADR: свободный режим — потом)?

## Главные риски (для сводки)
1. Календарь обещает уровни 11/12/14, а описан один; ловушки уровней 2–3 лишь гипотеза.
2. Метрика «≥30% ответивших на викторину открыли уровень» не измерима; нужны ссылка-счётчик и пинг победы.
3. Финал отеля на телефоне упирается в 8 переключателей и высоту экрана.
4. Нет «Поделиться» на победе — теряется самый дешёвый канал роста.
5. Новые темы выбирать по критерию уровня (поток, ловушка, выбор, потоковая картинка), а не по частоте: часть частых
   тем (секреты, ID, бэкап, мультитенантность) уровнем не становится.

## Три правки с наибольшим выигрышем
1. Следующие уровни — **rate limit, poison/DLQ, деплой+пробы**: переиспользуют палитру уровня 1, по одному новому
   кирпичу, у каждого есть ловушка «лекарство ломает».
2. На экране победы уровня 1 — кнопка «Поделиться» с числами табло и вызовом «а за 4 кирпича?»; в посте — фраза о двух
   решениях.
3. Убрать из календаря строки «+ уровень 11/12/14» до того, как уровни описаны; решение об уровнях 2–3 принять по итогам
   показа 3–5 посторонним (точка решения конца этапа 2).
