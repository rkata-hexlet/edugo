# Эпизод 03 «Distributed counter» — tech-expert по идее (22.10)

Вход: `docs/episodes/ideas.md` (Distributed counter), материал — `~/pet-projects/interview/tasks/system-design-ladder/README.md`
(раздел 2). Решение пользователя: два эпизода — 03 запись, 04 уникальные.

## Эпизод 03: ошибки наброска (зритель запомнит неправду)
1. **Горячая строка не теряет клики.** `UPDATE … SET clicks = clicks + 1` атомарен: на READ COMMITTED ждущий после
   COMMIT соседа перепроверяет строку и прибавляет к свежему значению. Счёт точный, беда — скорость. Голос: «считает
   верно, но по одному». Lost update — только у «прочитал в Go, записал число». REPEATABLE READ → ошибка сериализации
   (в описание, уровень в кадре не называем).
2. **Потолок числом не называть.** Замок держится до конца транзакции, включая fsync WAL; групповой коммит не
   помогает (следующий за той же строкой ждёт COMMIT). Потолок ≈ 1 / время коммита — от сотен до тысяч в секунду.
   В кадре — образ «по одному, строго по очереди», полоса с отметкой потолка.
3. **Чтения не ждут.** Редирект читает закоммиченную версию (MVCC). Сервис встаёт через **пул соединений**: ждущие
   UPDATE держат соединения, другим ссылкам не достаётся. Читателей в очереди за замком не рисовать. Счётчик — в
   отдельной таблице `link_stats(code, clicks)`.
4. **MVCC-раздувание — преувеличение:** `clicks` не в индексе → HOT, мёртвые версии чистит pruning. Максимум голосом
   «каждый плюс один — ещё и новая версия строки», лучше в описание.
5. **Sharded counter:** N добавить легко (чтение суммирует, что есть); трудно знать заранее, какая ссылка горячая
   (×16 строк на миллионы ссылок). **Главная цена — каждый клик по-прежнему транзакция**: очередь исчезает, записей и
   коммитов столько же. Случайный шард делит конфликт ≈ на N, а не убирает. `SUM` по 16 строкам дёшев и согласован.
6. **«Write-behind» неточен** (паттерн кэша). Ярлык: Write batching / Write coalescing.

## Батчинг: цена
- **Деплой важнее падения:** rolling update убивает все поды по очереди. Лечит graceful shutdown (SIGTERM,
  `signal.NotifyContext`, до `terminationGracePeriodSeconds`, по умолчанию 30 с). SIGKILL/OOMKill — потеря окна.
- **Двойной учёт при ретрае:** `+8431` закоммитился, ответ потерялся → повтор даст `+16862`. Рифма с неоднозначным
  исходом 01, только «Почта» — сама база. Лечит идемпотентный сброс: `INSERT INTO flushes(pod_id, seq) ON CONFLICT DO
  NOTHING` + `UPDATE` в **одной транзакции**.
- Свежесть: число отстаёт на окно сброса — голосом один раз.
- Go (в описание): `concurrent map writes` → мьютекс/атомики; сброс — подменить карту под мьютексом; сброс многих
  ссылок в порядке обхода `map` → deadlock между подами (сортировать или `UPDATE … FROM unnest(...)`).

## Где картинка соврёт
- Под ≠ один запрос: в очереди тысячи запросов от всех подов. Носитель — слоты пула у каждого пода, заполненные ждущими.
- В хуке не рисовать Redis-кэш редиректов (02 не выпущен).
- Реплика слона «я считаю, просто по одному» — честно; «не успеваю» про CPU — нет (ждут замок и коммит).

## Предложенная арка
**Хук:** все клики бьют `+1` в одну строку, очередь растёт, слоты пула заполнены, ждут и чужие ссылки.
**Норма:** один клик → `UPDATE +1` → COMMIT → 1 042 → 1 043; «база считает точно».

**Кейс 1 «Как выдержать поток кликов»** — табло «счёт точный / база справляется»:
| попытка | точный | справляется | что видно |
|---|---|---|---|
| `UPDATE +1` на клик | 🟢 | 🔴 | очередь за строкой, пул кончился |
| (опц.) `go func()` | 🟡 | 🔴 | ответ быстрый, горутины копятся у той же строки; рестарт — висящие теряются |
| sharded counter, 16 строк | 🟢 | 🟡 | очереди нет, но каждый клик — транзакция |
| копим в поде, сброс раз в 5 с | 🟡 | 🟢 | 4 записи/с вместо 10 тыс.; упадёт под — пропадут его секунды |

Sharded **раньше** батчинга сильнее: честная попытка решить в базе, её недостаток ведёт к батчингу.

**Кейс 2 «Под упал посреди сброса»** — табло «не теряем / не считаем дважды»:
| попытка | не теряем | не дважды | что видно |
|---|---|---|---|
| просто копим, деплой | 🔴 | 🟢 | rolling update — каждый под унёс свои секунды |
| graceful shutdown | 🟡 | 🟢 | деплой без потерь; kill -9 / OOM — потеря |
| сброс оборвался — повторяем | 🟢 | 🔴 | коммит был, ответ потерялся, `+8431` дважды (рифма: одна `done` — два письма) |
| ключ пачки в той же транзакции | 🟢* | 🟢 | `flushes(pod, seq)` + `ON CONFLICT DO NOTHING` |

\* только после graceful; kill -9 теряет окно — принимаем осознанно (статистика не деньги; для денег — сначала
надёжный журнал, Kafka). Одна фраза в финале. Минимум, если кейс 2 перегружает: деплой → graceful + фраза про ретрай.

**Итог:** очередь у строки → 16 строк без очереди, но поток тот же → пачки, 4 записи/с → ключ пачки гасит повтор.
**Финал (черновик):** «Горячей строке не нужен каждый клик: копим в поде, сбрасываем пачкой и даём пачке ключ, чтобы
повтор не посчитался дважды».

## Ярлыки 03
Hot row · lock contention (не head-of-line blocking) · Fire-and-forget · Sharded counter · Write batching / Write
coalescing · Graceful shutdown · At-least-once (с кадра поломки) → Idempotent flush (с кадра ключа).
Не использовать: Distributed lock, Exactly-once.

## Нить назад
- 01 (выпущен): рифма — кадр CAS «B и C ждали COMMIT пода A», повторить сценой; ключ идемпотентности у Почты → ключ
  пачки («получатель здесь — сама база, ключ она проверяет в той же транзакции»). Не «тот же head-of-line blocking».
- 02 (не выпущен): кэш и Redis не упоминать; мир (`links`, `x7Kp2`, поды, слон) брать можно. Хуки развести: в 03
  тонет **запись одной строки**, в 02 — чтения.

## В описание (не в ролик)
Redis INCR (рабочий вариант, но до выхода 02 не трогать), append-only лог / Kafka, rollup по времени
(`INSERT … ON CONFLICT (code, minute) DO UPDATE`), `synchronous_commit=off`, jitter сброса, deadlock при сбросе в
порядке `map`, `concurrent map writes`, REPEATABLE READ → ошибка сериализации.

## Эпизод 04 (уникальные) — коротко
- Номерок-cookie врёт: ничего не открывает; браузер предъявляет сам при каждом запросе; можно выбросить (очистка,
  инкогнито) и подделать (накрутка). «Карман у каждого браузера» — верно.
- Браузер без cookie неотличим от первого визита → новый `vid` на каждый клик → уникальные **завышаются**.
- Safari ITP может чистить хранилище редирект-доменов (bounce tracker); GDPR — согласие негде спросить. В описание.
- Не складываются даже на одном поде: между окнами сброса и днями — связь с батчингом 03.
- Пропущенная верная попытка: точное множество (`INSERT … ON CONFLICT DO NOTHING`, `SADD/SCARD`) — тоже сливается;
  беда в размере. HLL — «сливается **и** весит копейки».
- HLL: до 12 КБ (меньше на малых — sparse), ошибка 0,81% («около процента»), `PFMERGE` = union; нет пересечения,
  удаления, «кто именно». `PFADD` → 1 значит «изменился регистр», а не «vid новый».
- Носитель: 8–16 ящиков-регистров; `vid` → хэш битами → первые биты выбирают ящик, ящик хранит максимум ведущих нулей;
  повтор → тот же ящик, столбик не растёт; слияние — максимум по ящикам; оценка — интуиция монетки. Нельзя: `vid` в
  ящиках, столбики-счётчики, «12 КБ» как точный размер.
- Ярлыки: Unique visitors · Non-additive measure (или Count-distinct problem) · Exact distinct count · HyperLogLog.
  Табло «не завышаем / влезает в память»: по подам 🔴🟢, множество 🟢🔴, HLL 🟡🟢.

Источники: postgresql.org (transaction-iso, explicit-locking, storage-hot), redis.io (hyperloglogs), go.dev FAQ
(atomic maps), kubernetes.io (pod termination), webkit.org (tracking prevention).
