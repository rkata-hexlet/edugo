Эпизод 01. Конкурентная обработка задач

Как несколько подов делят одну очередь без дублей, простоев и зависших задач.

Интернет-магазин после заказа шлёт клиенту письмо. Задачи на отправку лежат в таблице Postgres, их разбирают три пода. Сначала все трое хватают одну задачу, и клиент получает три письма. Правильный вариант: 3 (единственный, tech-expert). Порядок вариантов при публикации перемешать (правильный не ставить

Почему варианты правдоподобны:

Разбор недавней загадки. Верный ответ: два письма; UPDATE пода B не изменит ни одной строки, задачу отметит только C.

[XX%] выбрали вариант 1: «одно письмо, отправка откатится». Понятная ловушка. База действительно сработала правильно: токен в строке уже чужой, и UPDATE пода B не изменил ни одной строки. [YY%] выбрали вариант 3, [ZZ%] вариант 4. В третьем упущено условие AND claim_token: записать может только тот, чей токен сейчас лежит в строке, а там уже токен C. В четвёртом — что B работает по старой проверке: он проверил срок до того, как завис, и после пробуждения не перепроверяет.

### 3.3 D. Шпаргалка (суббота)

Рамка серии «Цена · Когда нельзя · Что осталось за кадром». Ничего про сюжет, только то, чего нет в ролике (из
`docs/episodes/01-skip-locked.md`, раздел «Шпаргалка» и «Технические оговорки»).

-----
Шпаргалка к эпизоду 01: очередь задач на Postgres и lease  [жирный]

Захват и завершение:

UPDATE tasks
   SET status='in_progress', claim_token=gen_random_uuid(),
       attempts = attempts + 1, lease_until = now() + interval '30s'
 WHERE id IN (SELECT id FROM tasks
               WHERE (status='new' OR (status='in_progress' AND lease_until < now()))
                 AND attempts < 5
               ORDER BY id LIMIT 10
               FOR UPDATE SKIP LOCKED)
RETURNING id, claim_token, lease_until;

UPDATE tasks SET status='done' WHERE id=$1 AND claim_token=$2;

Завершение и продление проверяют число обновлённых строк: 0 — задачу уже перехватили, свой результат не записываем.

Цена:
1. SKIP LOCKED даёт не строгий порядок, а пропускную способность: FIFO здесь нет.
2. Долгой задаче нужен heartbeat: она сама продлевает аренду (UPDATE lease_until ... WHERE claim_token=$2; 0 строк — задачу перехватили, работу бросаем).
3. Счётчик попыток и «полка возвратов» (dead-letter) после N неудач, иначе отравленная задача будет ходить по кругу.
4. Индексы: частичный по status='new' и отдельный по lease_until для просроченных.

Когда нельзя:
1. Если получатель не умеет отсекать дубли (внешний API без ключа идемпотентности) и повтор недопустим, ни lease, ни другая очередь не дадут ровно одного эффекта. Остаётся выбрать меньшее зло: сначала действие, потом отметка — возможен дубль; сначала отметка, потом действие — возможна потеря. И добавить сверку с получателем.
2. Если продлевать аренду нечем, срок придётся ставить больше худшего времени задачи, и после падения пода задача будет ждать весь этот срок. Heartbeat в отдельной горутине это снимает, но держит аренду и за зависшей работой: нужен общий таймаут на задачу, а продление, обновившее 0 строк, значит, что задачу уже перехватили и работу пора бросать.
3. Если задач очень много: каждый захват и завершение — UPDATE, а значит мёртвые версии строк, нагрузка на VACUUM и разбухшие индексы. Для большого потока берут брокер очередей; Postgres-очередь хороша, пока задачи живут рядом с данными и их нужно менять в одной транзакции с ними.

Что осталось за кадром:
1. Владелец — токен захвата, а не имя пода: имя повторяется (несколько горутин, тот же hostname после рестарта в StatefulSet).
2. Пауза между проверкой срока и действием бывает не только от зависшего API: троттлинг CPU в контейнере, своп, SIGSTOP, пауза виртуальной машины. Это тот же check-then-act.
3. Срок под считает сам: засекает монотонный таймер до отправки запроса захвата и закладывает запас. Сверять lease_until, время базы, со своими настенными часами ненадёжно: часы пода и базы расходятся и могут прыгнуть при синхронизации. И даже точный таймер не спасает от паузы сразу после проверки — от неё запись защищает только токен.
4. Если у получателя нет Idempotency-Key, ключ хранит отправитель: таблица отправленных, куда ключ пишется до вызова или после. Окно дубля сужается, но не закрывается: под может упасть между вызовом и записью.
5. Долгая транзакция «на всё время работы» держит соединение и горизонт xmin (VACUUM не чистит); защита idle_in_transaction_session_timeout по умолчанию выключена, а пропавший узел Postgres замечает по TCP keepalive, на Linux около двух часов.
6. Всё показано на READ COMMITTED, умолчании Postgres. Там проигравший в гонке за одну строку дожидается коммита соперника, перепроверяет WHERE и получает 0 строк. На REPEATABLE READ он вместо этого получит ошибку сериализации, и запрос придётся повторить.

Что у вас на практике: сколько стоит lease и как вы продлеваете?
-----
