# Эпизод 05 — «Уровни изоляции транзакций» (рабочее название)

Тема: два заказа одновременно в интернет-магазине. Что видит каждая транзакция, почему READ COMMITTED теряет
обновление в коде «прочитал → посчитал → записал», чем отвечает REPEATABLE READ (ошибка сериализации и повтор) и
почему ему не виден write skew, который ловит SERIALIZABLE.

Разборы: tech-expert — `docs/reviews/05-tech-expert-idea.md`, scriptwriter — `docs/reviews/05-scriptwriter-arc.md`.
Подача — эталон 01, начало «система → хук». Мир новый — интернет-магазин (02–04 — сокращатель ссылок).

Статус: **v1 (23.10) — MVP `?scene=05`, 22 кадра, синтез.** Решение пользователя 23.10: **два ролика** — 05 = кейс
«последняя кружка» (ниже), 06 = слот курьера (раздел «Эпизод 06»); покупатели — Аня и Борис. После MVP tech-expert
(модель верна; правки текста взяты: финал без «не правильнее данные», ROLLBACK после 40001, «строка заперта для записи»,
FOR UPDATE одной фразой, «затёр бы изменение, которого не видел» вместо «решение на устаревших данных», MySQL с InnoDB).
Закадр — `05-narration.md`.

## Арка
Знакомство (витрина, последняя кружка, Аня и Борис, поды A и B, Postgres с `products` и `orders`) → **хук:** оба
нажали «Купить» одновременно — `stock = 0`, а заказов два (рифма с 01: одна строка `done`, два письма) → норма: по
очереди, Борис получает «Нет в наличии» → **кейс 1** «Как не продать последнюю кружку дважды»: наивное
read-modify-write теряет обновление → атомарный `UPDATE … WHERE stock > 0` (база ждёт коммита и перепроверяет условие
на свежей версии; ⟲ Вернёмся: очередь задач 01) → ⟲ Иначе: логика не влезает в один UPDATE — тот же наивный код на
REPEATABLE READ: снимок замер, запись упирается в новую версию → 40001 → ↺ повтор с BEGIN → «Нет в наличии» →
**кейс 2** «Как не перегрузить курьера» ломает «починили»: слот на 3 заказа, занято 2, оба на RR видят «2 из 3» и
вставляют разные строки — никто никого не ждёт, у курьера четыре коробки (рифма с хуком) → SERIALIZABLE: первый
коммит выигрывает, второму 40001 при записи или на COMMIT → ↺ → «слот занят» → ⟲ Иначе: правило в одной строке
слота (`booked < cap`, рифма с 1.2) → итог повтором сцен.

Главный «ага»: **база защищает только то, что видит в записи: условие в одной строке или конфликт, который ловит
уровень изоляции; выше изоляция — не правильнее данные, а громче ошибка, и транзакцию повторяем.**

## Мир и персонажи
- **Витрина** слева: «Кружка · осталось 1», кнопка «Купить» — пока голос говорит об остатке, потом её заменяет `stock`.
- **Покупатели Аня и Борис** — аватары; всегда жмут одновременно, Борис всегда второй. Реакции: «Заказ принят ✓»,
  серая плашка «Нет в наличии» (ответ магазина — не ошибка базы).
- **Поды A (Аня) и B (Борис)** — сервис оформления заказа. Мысли-заблуждения: «Вижу 1 — моя!», «2 из 3 — место есть!»;
  зачёркиваются при отказе.
- **Postgres-слон** — строг в формальном, бизнес-правил не знает («Четыре? Я не считал.»).
- **Таблицы** `products` (`stock`), `orders`; в кейсе 2 — слот «18–20, мест 3» (заказы в `orders` с `slot`), в 2.3 —
  строка `slots` с `booked`/`cap`.
- **Курьер** (кейс 2) в жилете «макс. 3», коробки в руках; молчит позой.
- **Носитель снимка — по слоям** (tech-expert: не копия у пода, а видимость над версиями строки):
  хук — только стрелка чтения; 1.1 — **стопка версий строки** (новая `stock 0` ложится поверх, старая бледнеет);
  1.2 — после ожидания замка база перепроверяет условие на верхней версии; 1.3 — **линия-горизонт** с часами БД
  «видит: до 12:00:01», встаёт **на первом запросе** (не на BEGIN), на RR замирает. Запись — всегда толстая стрелка к
  верхней версии через замок; расхождение стрелки чтения и записи = 40001. Часы БД — только с 1.3.
- **40001** — красная молния + «↺ заново с BEGIN»; не путать с «Нет в наличии».

## Эпизод 06 — слот курьера (write skew)

сцены REPEATABLE READ из 05.

## Развилки (решены 23.10: два ролика, Аня и Борис)
1. **Один ролик или два.** tech-expert: один (~52 кадра, делить при > 6:30). scriptwriter: два — 05 кейс 1, 06 кейс 2
   (~8 новых терминов, два разных «ага», курьер — сильный отдельный хук; 06 открывается повтором сцены 1.3). Мир
   магазина тогда — 05, 06 и deadlock (07). **Моя рекомендация — два**: в недельном ритме это два законченных ролика,
   кейс 1 самодостаточен, а кейс 2 своим хуком только выигрывает.
2. Покупатели с именами (Аня, Борис — как в 04) или безымянные «покупатель 1/2».

## В описание (не в ролик)
Оптимистичная `version`; атомарный `stock - 1` на RR — тоже 40001; MySQL InnoDB RR теряет обновление молча, умолчания
PG/MySQL/Oracle; как задать уровень в pgx / database/sql; повтор в Go (`40001`, `40P01` — повторять, `23505` — нет;
лимит и backoff; внешние эффекты вне транзакции); `CHECK (stock >= 0)`; `FOR UPDATE` блокирует вставку с FK →
`FOR NO KEY UPDATE`; read skew в отчёте (RR READ ONLY); частичный уникальный индекс для промокода.
