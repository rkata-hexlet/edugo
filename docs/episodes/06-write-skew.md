# Эпизод 06 — «Курьер и четыре коробки» (write skew)

Тема: правило «в слоте не больше трёх заказов» держится на подсчёте разных строк. REPEATABLE READ его не защищает
(write skew), SERIALIZABLE ловит через метки чтения и цикл зависимостей (SSI) ценой повторов, а счётчик в строке
слота сводит конфликт к одной строке — атомарный UPDATE из 05.

чек-лист подачи — `docs/reviews/06-recurring-mistakes.md`. Мир — интернет-магазин эпизода 05 (второй эпизод мира).
Закадр — `06-narration.md` (выгрузка из `script.ts`).

Статус: **v2 (24.10) — 34 кадра после learning-designer, tech-writer, tech-expert; звук и отрисовка отполированы; автономно** (пользователь: «делай полностью без меня»).

## Арка
Отсылка (кадр 40001 эпизода 05; RR и снимок определены голосом — ролик работает без 05) → «мы перевели весь сервис
на RR» → знакомство (поды = экземпляры сервиса на Go, слот 18–20 на три заказа, `slots.cap`, `orders`, код: подсчёт в
отдельном чтении, запись — новая строка; «казалось бы, безопаснее») → **хук** на RR: оба видят «2 из 3», вставляют
разные строки, никто не ждёт, оба коммитят — четыре коробки → норма по очереди: Борис — «слот занят» → **кейс «Как не
перегрузить курьера?»** (голос: «почему RR, который спас кружку, промолчал?»):
- 2.1 оба посчитали до вставок («это не устаревшие данные — не помог бы и READ COMMITTED») → вставка 05: что сверяет RR
  (строку, которую меняют или удаляют, после снимка) → «сверять не с чем», оба коммита проходят → `Write skew`;
- 2.2 SERIALIZABLE: одна строка кода → «не очередь и не замок; результат как по очереди в каком-то порядке, иначе 40001,
  повторяет наш код» (код проверяет ошибку каждого запроса) → метки чтения (predicate lock) → вставка A: «B должен был
  идти раньше A» → вставка B: цикл, «ни в каком порядке так не выйти» (`Serializable · SSI`) → A коммитит, B уже
  обречена, 40001 на COMMIT (может прийти на любом запросе) → повтор → «слот занят»; критерий «без повтора» вводится
  здесь голосом → цена: повторы чаще, перестраховка;
- 2.3 вставка 05: атомарный UPDATE кружки → счётчик `booked` одним запросом → «вернём READ COMMITTED: на RR снова 40001»
  → B ждёт → перепроверка `booked < cap` → 0 строк, без повтора → `Atomic update`, FOR UPDATE одной фразой; цена —
  строка заперта до коммита (распродажа);
- когда что (два кадра): счётчик — одно число в одной строке; но он производные данные (оформление, отмена, перенос,
  админка); на SERIALIZABLE хранить нечего — каждый путь пересчитывает сам, пока все на SERIALIZABLE;
- итог повтором трёх сцен по развилке: беда → «сводится к одной строке — UPDATE с условием на READ COMMITTED» → «не
  сводится — SERIALIZABLE и повтор».

## Мир и персонажи
- **Магазин** справа: Аня и Борис, кнопка «Заказать»; ответы — «Заказ принят» / «Слот занят» (ответ нашего кода,
  не ошибка базы).
- **Курьер** под магазином (кепка, жилет): фургон, коробка = закоммиченный заказ, лента — цвета покупателя; вместимость
  три. Четвёртая — на крыше, кузов просел, курьер хватается за голову (по очереди: штамп → коробка → курьер); при трёх
  — рука вверх. Нить-вопрос — «?» над фургоном, пока исход не ясен.
- **Поды A и B**, мысль-заблуждение «2 из 3 — место есть!» висит, пока под в неё верит.
- **Postgres** (слон) слева сверху; таблицы `slots` (id 7 · 18–20 · cap 3 [· booked]) и `orders` (заказы слота 7).
- Носители: сверка RR у пода («INSERT · сверять не с чем ✓»); метка чтения SSI — пунктирная рамка цвета пода вокруг
  заказов слота и места под ними (не замок); зависимость — дуга от чужой вставки; цикл — две встречные дуги и пилюля
  «цикл»; откат на 40001 — зачёркнутый «призрак» строки; замок строки слота в 2.3.

## Обложка и финал
- Обложка: «Курьер и четыре коробки» / «Мест в слоте три, а заказов четыре. Как не перегрузить курьера?»
- Финал (`Scene.meta.outro`): «Если правило держится на подсчёте разных строк, ни READ COMMITTED, ни REPEATABLE READ его не защитят. Сведите
  правило в одну строку с условием в UPDATE, а если не выходит, берите SERIALIZABLE и повторяйте транзакцию».

## В описание (не в ролик)
Гранулярность меток (страницы индекса, вся таблица при seq scan), индекс по `slot_id`; 40001 бывает и на чтении;
при обратном порядке коммитов проигрывает A; откат A — B проходит; FOR UPDATE на слоте работает только на READ
COMMITTED (на RR снимок берётся до ожидания замка); счётчик на RR — 40001 и повтор; `pg_advisory_xact_lock`;
`EXCLUDE USING gist` для пересечений интервалов; `CHECK (booked <= cap)`; Oracle SERIALIZABLE — snapshot isolation,
write skew не ловит; MySQL SERIALIZABLE — блокирующие чтения; `SERIALIZABLE READ ONLY DEFERRABLE`; повтор в Go
(`40001`, лимит, backoff, внешние эффекты вне транзакции); «phantoms causing write skew» (DDIA, гл. 7). Ещё (tech-expert v2): в общем случае SSI ищет две rw-зависимости подряд, а не весь цикл — поэтому ловит каждый
цикл и иногда прерывает без него (README-SSI); 40001 до COMMIT → pgx на Commit вернёт ErrTxCommitRollback, обёртка
повтора должна смотреть ошибку каждого запроса; счётчик триггером закрывает все пути в базе.
