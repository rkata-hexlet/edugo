# Эпизод 06 — «Курьер и четыре коробки» (write skew)

Тема: правило «в слоте не больше трёх заказов» держится на подсчёте разных строк. REPEATABLE READ его не защищает
(write skew), SERIALIZABLE ловит через метки чтения и кольцо зависимостей (SSI) ценой повторов, а счётчик в строке
слота сводит конфликт к одной строке — атомарный UPDATE из 05.

Разборы: tech-expert — `docs/reviews/06-tech-expert-arc.md`, scriptwriter — `docs/reviews/06-scriptwriter-arc.md`,
чек-лист подачи — `docs/reviews/06-recurring-mistakes.md`. Мир — интернет-магазин эпизода 05 (второй эпизод мира).
Закадр — `06-narration.md` (выгрузка из `script.ts`).

Статус: **v1 (24.10) — сценарий и MVP `?scene=06`, автономно** (пользователь: «делай полностью без меня»).
Решения пользователя 24.10: арка кейса RR → SERIALIZABLE → ⟲ счётчик в строке слота; FOR UPDATE — одной фразой;
отсылка к 05 — его сценой RR.

## Арка
Отсылка (кадр 40001 эпизода 05: оба писали в одну строку `stock`, RR поймал) → «мы перевели весь сервис на RR» →
знакомство (курьер, слот 18–20 на три заказа, `slots.cap`, `orders`, код на Go: подсчёт в отдельном чтении, запись —
новая строка; «казалось бы, безопаснее») → **хук** на RR: оба видят «2 из 3», вставляют разные строки, никто не ждёт,
оба коммитят — четыре коробки (рифма с хуком 05) → норма по очереди: Борис — «слот занят» → **кейс «Как не
перегрузить курьера?»**: 2.1 почему RR молчит (снимок B без заказа Ани; RR сверяет только строку, которую меняешь сам —
«своя новая строка ✓»; `Write skew`) → 2.2 SERIALIZABLE (не очередь и не замок; метки чтения, predicate lock;
вставки → кольцо; A коммитит, B — 40001 на COMMIT; повтор нашим кодом → «слот занят»; цена: повтор любой транзакции,
все пишущие на SERIALIZABLE) → 2.3 ⟲ счётчик `booked` в строке слота на READ COMMITTED (B ждёт, перепроверка
`booked < cap` → 0 строк, без повтора; `Atomic update`; цена — копия подсчёта и горячая строка) → когда что →
итог повтором трёх сцен.

Главный «ага»: **REPEATABLE READ ловит запись в одну и ту же строку, а не решение по прочитанному; правило на подсчёте
разных строк сводим в одну строку или поднимаем изоляцию до SERIALIZABLE и повторяем.**

## Мир и персонажи
- **Магазин** справа: Аня и Борис, кнопка «Заказать»; ответы — «Заказ принят» / «Слот занят» (ответ нашего кода,
  не ошибка базы).
- **Курьер** под магазином: фургон и коробки в кузове по числу закоммиченных заказов слота; вместимость три. Четвёртая
  коробка — сверху, кузов просел, курьер растерян. Нить-вопрос — «?» над фургоном, пока исход не ясен.
- **Поды A и B**, мысль-заблуждение «2 из 3 — место есть!» висит, пока под в неё верит.
- **Postgres** (слон) слева сверху; таблицы `slots` (id 7 · 18–20 · cap 3 [· booked]) и `orders` (заказы слота 7).
- Носители: бледные заказы, которых снимок пода не видит (линия снимка — цвет пода); сверка RR у пода
  («своя новая строка ✓»); метка чтения SSI — пунктирная рамка цвета пода вокруг заказов слота и места под ними (не
  замок); зависимость — нить от чужой вставки к рамке; кольцо — две встречные нити; замок строки слота в 2.3.

## Обложка и финал
- Обложка: «Курьер и четыре коробки» / «Мест в слоте три, а заказов четыре. Как не перегрузить курьера?»
- Финал (`Scene.meta.outro`): «Если правило держится на подсчёте разных строк, REPEATABLE READ его не защитит. Сведите
  правило в одну строку с условием в UPDATE, а если не выходит, берите SERIALIZABLE и повторяйте транзакцию».

## В описание (не в ролик)
Гранулярность меток (страницы индекса, вся таблица при seq scan), индекс по `slot_id`; 40001 бывает и на чтении;
при обратном порядке коммитов проигрывает A; откат A — B проходит; FOR UPDATE на слоте работает только на READ
COMMITTED (на RR снимок берётся до ожидания замка); счётчик на RR — 40001 и повтор; `pg_advisory_xact_lock`;
`EXCLUDE USING gist` для пересечений интервалов; `CHECK (booked <= cap)`; Oracle SERIALIZABLE — snapshot isolation,
write skew не ловит; MySQL SERIALIZABLE — блокирующие чтения; `SERIALIZABLE READ ONLY DEFERRABLE`; повтор в Go
(`40001`, лимит, backoff, внешние эффекты вне транзакции); «phantoms causing write skew» (DDIA, гл. 7).
