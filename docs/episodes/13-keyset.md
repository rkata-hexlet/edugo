# Эпизод 13 — «Keyset-пагинация» (рабочее название)

Тема: список отдают страницами. OFFSET считает позицию заново на каждом запросе — список живой, позиции едут, гость видит
карточку дважды или не видит вовсе; на глубине база читает и выбрасывает всё до страницы. Keyset — запоминаем, где остановились
(закладка по уникальному порядку), а не номер позиции. Мир — **сервис бронирования отеля** (гость, рамка «Сервис бронирования» с
подами, Postgres-слон). Ветка от `episode/12-saga`, выпуск после 12. Эпизод понятен без прошлых.
Разборы: `docs/reviews/13-tech-expert-arc.md` (техническая основа, «не обещаем», SQL, числа), `docs/reviews/13-scriptwriter-arc.md`
(мир, носители; раскадровка v1 — **устарела**, см. арку v2), разборы MVP v1: `docs/reviews/13-{scriptwriter,learning-designer,tech-expert}-mvp.md`.

Статус: **MVP v2 (22 кадра) собран 29.10 — ждёт приёмки пользователем (фаза 1).**

## Решения
- 29.10 — тема и мир (пользователь): keyset-пагинация, мир отеля, от ветки 12. Две сцены одного мира: выдача гостю по цене
  «Показать ещё» и выгрузка броней партнёру страницами; переход — камерой (поды и слон те же).
- 29.10 — **арка v2** (пользователь выбрал после разбора MVP v1 командой). Почему: в v1 беда скорости OFFSET звучала только после
  победы закладки, индекс появлялся только у закладки — зритель выносил «решили потери, получили тормоза». Теперь **все беды OFFSET —
  до закладки**, закладка чинит их все, потом честная цена.
- Одна шкала на весь эпизод — табло из трёх ламп **«не пропало / не дважды / быстро»**; лампа, которую кадр не проверяет, серая.
- Порядок в таблице не хранится: таблица `offers` — в порядке добавления (id растёт на 1); порядок даёт `ORDER BY` заново на каждый
  запрос (правка пользователя 29.10, три раза).

## Картинка
- **Таблица по id показана один раз (кадры 2–3)**, потом сворачивается в узкую полоску-склад сбоку: строки по id, новые — в конец,
  проданные — зачёркнуты; там же видно изменение между нажатиями.
- **Выдача пересобирается на глазах по нажатию**: старый список гаснет, карточки выстраиваются по `price, id`, поверх — окно
  страницы («отсчитать 5 / взять 5» у OFFSET, «от закладки — 5» у keyset). Строки ниже страницы приглушены (черта LIMIT).
- Копий карточек нет: телефон гостя — окно вокруг границы страниц (5–6 карточек), а не вся лента. На экране ≤ ~15 карточек.
- Закладка — флажок у **значения** (у карточки), не у позиции.
- Индекс в кейсе 1 не показываем. В выгрузке индекс `(created_at, id)` есть **с первого кадра** — отдельная структура рядом с
  таблицей, порядок в ней Postgres поддерживает при вставке; OFFSET идёт по нему от первой брони, закладка — сразу от себя.
- SQL в панели подсвечивается по частям в такт слову (ORDER BY, LIMIT/OFFSET, WHERE) — в шлифовке.

## Арка v2 (≈ 20 кадров, закадр ≈ 1100 слов, ≈ 7 мин)
**Знакомство**
1. Контекст и тизер: «Это сервис бронирования отеля. Гость ищет номер… жмёт „Показать ещё“ — и видит ту же карточку». Гость:
   «Это я уже видел.»
2. Мир: гость, поды, слон. Таблица `offers` — в порядке добавления, по цене никак, и даже на порядок добавления рассчитывать нельзя.
3. Запрос `ORDER BY price, id LIMIT 5`: выдача собирается из таблицы на глазах, таблица уходит в полоску. Голос: сортирует заново на
   каждый запрос; `id` — чтобы при равной цене порядок был однозначен. Слон: «Порядок? Как в запросе скажете.» (В жизни 20–50 — голосом.)
4. Норма: «Показать ещё» — `LIMIT 5 OFFSET 5`: слон **каждый раз с начала** отсчитывает пять и отдаёт следующие пять. Десять карточек
   без повторов. Слон: «Моё дело — отсчитать.»

**Кейс 1 из 2 «Чем плох OFFSET?»** — табло три лампы.
5. Плашка.
6. Дубль (хук): гость на первой странице; отель снизил цену — в полоске «+ Пирс 3 200 ₽»; нажатие — выдача пересобирается, всё
   сдвинулось на одну, «Причал» второй раз. 🔴 не дважды. Ярлык Offset pagination.
7. DELETE (два кадра по образцу INSERT): другой гость купил последний номер в «Соснах» — `DELETE FROM offers WHERE id = 4419`,
   в таблице строка зачёркнута на месте, «удалена»; нажатие — выдача сдвигается вверх, «Лагуна» проваливается в щель между
   страницами и машет «Я здесь!» (зритель видит, гость — нет). 🔴 не пропало.
7а. UPDATE (два кадра): «Бриз» 4 200 → 6 000 — `UPDATE offers SET price = 6000 WHERE id = 4417`, строка на месте, «было 4 200 ₽»;
   нажатие — «Бриз» уезжает на вторую страницу: «Лагуна» в щели и «Бриз» второй раз (у гостя на первой странице — 4 200, как видел).
   🔴🔴 сразу. Гость: «Опять «Бриз»?»
8. Камерой к выгрузке: тот же сервис отдаёт партнёру **вчерашние брони** (закрытый период — ничего не добавляется) страницами по
   1 000, `ORDER BY created_at, id`. Индекс `(created_at, id)` рядом с таблицей.
9. Глубина: страница 2000 — `OFFSET 1 999 000`: по индексу от первой брони, **прочитано 2 000 000, отдано 1 000** (счётчики — после
   слов «читает и выбрасывает»). Кофе бухгалтера остывает от страницы к странице, корзина слона переполнена. За всю выгрузку ≈ 2 млрд —
   голосом. Первые страницы летят — для неглубоких смещений OFFSET хорош. 🔴 быстро. Ярлык Deep pagination.
10. Итог кейса: 🔴🔴🔴. Корень один: OFFSET помнит **номер позиции**, а позицию база вычисляет заново на каждом запросе — от начала.

**Кейс 2 из 2 «Закладка вместо счёта»**
11. Плашка.
12. Контекст: гость снова листает. Запоминаем не номер, а значение последней показанной — флажок «4 900». `WHERE price > 4900
    ORDER BY price, id`: у трёх номеров по 4 900 закладка одна — «Лагуна» не придёт. 🔴🟢⚪. Ярлык Keyset pagination.
13. `price >= 4900`: «Утёс» и «Причал» снова. При ничьих больше страницы — та же страница по кругу. 🟢🔴⚪.
14. Пара: закладка помнит `(price, id)` — «4 900 | 4415»; `WHERE (price, id) > (4900, 4415)` (row comparison — голосом). Сортировка
    была верна с самого начала — неполна была закладка; id в сортировке нужен и OFFSET, поэтому он там с кадра 3. Ярлык Tie-breaker.
    Дальше те же три изменения, что в кейсе 1, по два кадра (таблица + SQL → нажатие):
    - INSERT «Пирс» — вторая страница с «Лагуны», без повторов 🟢 не дважды; «Пирс» встал позади закладки — гость его не увидит
      (закладка не снимок).
    - DELETE «Сосен» — вторая страница ровно с «Лагуны» 🟢 не пропало.
    - UPDATE «Бриз» 4 200 → 6 000 — «Лагуна» на месте, «Бриз» встал дальше закладки и пришёл второй раз; лампы не трогаем: карточка
      сама сменила ключ, закладка ей ничего не обещала. Здесь же честная гарантия: «кто стоял на месте, придёт ровно раз»; снимок на
      всё листание держал бы долгую транзакцию — одна фраза.
15. Выгрузка с закладкой: `WHERE (created_at, id) > ($1, $2)` — по индексу сразу к закладке, **прочитано 1 000, отдано 1 000** на
    любой глубине. Ничья по `created_at` — та же пара с id. 🟢🟢🟢.
16. Цена: на «страницу 812» не прыгнуть — гость жмёт, слон: «Закладки там нет.» Назад листать можно (обратный запрос). Сколько всего
    страниц — отдельный `COUNT(*)` при любом способе (голосом, не как минус закладки). Быстро — только с индексом ровно под порядок.
17. (Честная гарантия — перенесена в кадры INSERT и UPDATE против пары, п. 14.)

**Итог**
18. Матрица OFFSET / закладка на три лампы; под закладкой серая подпись цены «нет перехода на страницу N». Голос: «OFFSET считает
    позиции — ошибается, когда они сдвигаются, и тормозит, когда их много. Закладка помнит значение — и чинит оба. Платим: нельзя
    прыгнуть на страницу N.»
19. Повтор образов: дубль, «Лагуна» в щели, близнецы и флажок-пара, кофе и тысяча/тысяча. Гость: «Этого я ещё не видел.»
20. Outro: «Не отсчитывай страницы — запоминай, где остановился.»

## Правила подачи (не нарушать) — из разборов tech-expert
- Не «база пропускает» — «читает и выбрасывает»; в кадре число прочитанных строк, а не миллисекунды.
- Не обещаем: «OFFSET всегда медленный» (медленно только глубоко); «keyset даёт снимок»; «keyset никогда не теряет строк»;
  «увидел каждое предложение» без оговорки. Гарантия одна: строка, что всё листание стояла на месте и не меняла ключ, придёт ровно раз.
- Сортировка во всех запросах эпизода — `ORDER BY price, id` (и в попытках `>`/`>=`); tie-breaker не подаём как особенность keyset.
- Keyset быстрый только с индексом ровно под порядок; без индекса каждая страница читает всё. Кортеж — row comparison, не OR-форма.
- «Всего страниц» — не цена закладки (COUNT нужен и OFFSET). Цена — нет прыжка на страницу N; назад — можно.
- Выгрузка — закрытый период; «новые брони встают в конец» не говорим (поздний коммит ложится в середину).
- SQL совпадает с кадром: 5 карточек — `LIMIT 5`; выгрузка — `LIMIT 1000`.
- Слово «курсор» в ролике не звучит; cursor pagination, непрозрачный токен — в описание.
- Ярлыки — по разу: Offset pagination (6), Deep pagination (9), Keyset pagination (12), Tie-breaker (14). Голосом: seek method,
  row comparison.
- Числа: таблица 4412–4421 по порядку добавления, «Пирс» 4422; ничья по 4 900 — 4413/4415/4418; закладка `(4900, 4415)`; продажа —
  «Сосны» 4419; 2 000 000 броней по 1 000, брони от `880412`, закладка `('2026-03-14 09:12:05', 880412)`.

## За рамками эпизода (в описание)
Синхронизация «всё после последнего id» теряет строки (`bigserial` раздаёт номера не в порядке коммитов); NULL в ключе; смешанные
направления сортировки (`price ASC, id DESC` — row comparison не годится); курсор как непрозрачный токен; реплики и read-your-writes;
фильтры (город, даты) — индекс `(city_id, price, id)`, а при цене, вычисляемой в запросе, индекса под порядок нет: закладка лечит дубли
и пропуски, но не скорость; снимок / `WITH HOLD` на всё листание и VACUUM.
