# Эпизод 02 — «Кэш перед базой» (рабочее название)

Тема: сервис коротких ссылок читает в сотни раз чаще, чем пишет; кэш (Redis, cache-aside) снимает
нагрузку с Postgres. Две главы: **кейс 1** — кэш врёт после правки ссылки (инвалидация: порядок «база →
удалить ключ», страховка TTL); **кейс 2** — горячий ключ (один узел Redis тонет → локальный кэш L1 в
каждом поде → L1 врут после правки → короткий TTL / рассылка «сбрось ключ»).

## Арка
Хук — проблема в чистом виде: ссылку выложил крупный Telegram-канал, каждый клик — запрос в Postgres, база
захлёбывается (очередь запросов, страница открывается секундами). Норма — cache-aside: под спрашивает
Redis, промах → база → кладёт копию с TTL; дальше клики отвечает Redis, база отдыхает.
Кейс 1 ломает «починили»: автор исправил опечатку в адресе, а посетители ещё час попадают на старый
(404) — кэш врёт. Попытки от наивной к верной на одинаковом старте. Кейс 2 ломает снова: ссылку
подхватили ещё каналы — кэш-то есть, но **тонет один узел Redis, остальные простаивают** (рифма с
хуком: там тонул слон, тут — узел 3). Главный «ага»: **кэш — копия, она всегда немного отстаёт;
наша работа — сделать окно вранья коротким и ограниченным, а не притворяться, что его нет.**

## Мир и персонажи
- **Таблица `links`** (Postgres, слева вверху): `code`, `long_url`. В центре внимания —
  `x7Kp2 → shop.example/sale`, ещё две ссылки фоном и строка «… ещё миллионы ссылок».
- **Слон-Postgres** — тот же кладовщик из эпизода 01, в шапке. Ворчит, когда его дёргают по одному и
  тому же («Опять x7Kp2?»); голос при этом не говорит «база лезет на диск» — строка в памяти, дорого
  само соединение и запрос (tech-expert). Носитель нагрузки — полоса с отметкой потолка, без чисел ёмкости.
- **Redis** — панель под таблицей, **сбоку от пути** (cache-aside: под сам ходит и в Redis, и в базу,
  сам кладёт копию; Redis в базу не ходит — tech-expert). Записи `ключ → значение` и полоса TTL. В кейсе 2
  панель становится кластером: узлы в ряд, у каждого полоса нагрузки; ключ живёт в слоте одного узла.
- **Поды A, B, C** — копии сервиса ссылок, стоят на месте (как в 01). Стрелки кадра: к Redis (попал —
  сплошная, промах — короткая с ✕), к строке базы мимо Redis, `SET`/`DEL` — к Redis, ответ — к браузерам.
  В кейсе 2 у каждого пода — карман L1 (`x7Kp2 → …`) со своей полосой срока.
- **Браузеры** (справа, на месте Почты) — журнал ответов посетителям: `→ /sale` ✓ или `→ /sale · 404`
  красным. Внешний мир: ни база, ни кэш его не видят. Поток кликов — образом в шапке панели.
- **История правки:** магазин перенёс распродажу на `shop.example/promo`, а старую страницу закрыл в ту
  же минуту — автор правит ссылку (через под A, значок карандаша). Красным — только ответ, который
  **расходится с закоммиченным** в базе (до COMMIT старый адрес — не враньё, tech-expert).
- **Часы** — для TTL и окна вранья; назад не идут. Одни часы — допустимое упрощение (TTL Redis идёт по
  часам Redis, L1 — по таймеру пода).

## Табло (лампы сверяет тест по модели)
Шкала свежести: 🟢 — врёт не дольше миллисекунд; 🟡 — враньё ограничено (секунды или только при сбое);
🔴 — после каждой правки врёт до конца долгого TTL. Нагрузка: 🟢 полоса в норме, 🟡 высоко, 🔴 за потолком.
| кейс 1 «ответ свежий / база держит» | | кейс 2 «ответ свежий / узел не тонет» | |
|---|---|---|---|
| кэш на час | 🔴 🟢 | кэш как есть | 🟢 🔴 |
| короткий TTL (10 с) | 🟡 🟡 | больше узлов | 🟢 🔴 |
| удалить ключ, потом база | 🔴 🟢 | локальный кэш L1 | 🟡 🟢 (лампа свежести — в твисте) |
| база, потом удалить ключ | 🟢 🟢 | L1 + рассылка «сбрось» | 🟢 🟢 |
| …а если DEL не дошёл | 🟡 🟢 | | |

## Кадры (v2)
**0. Хук**
1. Ссылку `sho.rt/x7Kp2` выложил крупный Telegram-канал — 20 000 кликов/с (образ). Каждый клик → под →
   `SELECT long_url FROM links WHERE code='x7Kp2'`. Полоса базы за потолком (кончились соединения —
   запросы в очереди), браузеры: «⏳ 4 с». Postgres: «Опять x7Kp2? Я же только что отвечал!»

**Знакомство и норма**
2. Таблица `links`: короткий код → длинный адрес.
3. Поды — копии сервиса ссылок; клик: под A читает адрес из базы и отвечает браузеру редиректом → ✓.
4. Рядом с базой ставим Redis — копию в памяти (пусто).
5. Под A: `GET x7Kp2` → промах → `SELECT` → `SET x7Kp2 /sale EX 3600` → ответ ✓ (SQL-панель).
6. Поды B и C: `GET` → попадание → ✓ ✓, база не тронута; полоса базы зелёная. Ярлык **Cache-aside**.

**Кейс 1 из 2** — плашка: «Автор поменял ссылку. Что увидят посетители?»
- *Кэш на час*
7. Магазин перенёс распродажу на `/promo`; автор правит: под A `UPDATE … COMMIT` (SQL). В базе `/promo`,
   в Redis `/sale`, TTL ещё 40 мин.
8. B и C: `GET` → попадание `/sale` → 404 ×2. Ярлык **Stale cache**.
9. Часы +39 мин: всё ещё 404 → 🔴 🟢.
- *Короткий TTL (10 с)* — штамп «⟲ Иначе: срок 10 секунд»
10. Та же правка; 404 — пара секунд; часы +2 с (ключ с TTL 10 с положен 8 с назад): срок вышел → B промах → база → `/promo` ✓.
11. Цена: редкие ссылки (миллионы) открывают реже раза в 10 с — для них кэш почти всегда пуст, промахи
    идут в базу, полоса базы жёлтая → 🟡 🟡.
- *Удалить ключ, потом база* — штамп
12. A: `DEL x7Kp2`, затем `BEGIN; UPDATE …` (не закоммичено).
13. B: `GET` → промах → `SELECT` → `/sale` **сразу, без ожидания** (чтение не ждёт чужую транзакцию —
    видит последнее закоммиченное) → `SET /sale EX 3600`.
14. A: `COMMIT`. C: `GET` → `/sale` → 404 — и так весь час → 🔴 🟢. Ярлык **Race condition**.
    Голосом: на горячем ключе в эту щель кто-то попадает почти наверняка.
- *База, потом удалить ключ* — штамп
15. A: `BEGIN; UPDATE …`; B: `GET` → `/sale` ✓ (правки ещё нет — не враньё).
16. A: `COMMIT` → `DEL`. Голосом: окно — миллисекунды между ними.
17. B и C: промах → база → `/promo` → `SET` → ✓ ✓ → 🟢 🟢. Ярлык **Cache invalidation**. Голосом: удаляем,
    а не перезаписываем — следующий промах сам возьмёт из базы свежее.
- *…а если DEL не дошёл* — штамп «⟲ Вернёмся: COMMIT прошёл»
18. A: `COMMIT` — и падает, `DEL` не выполнен.
19. B и C: `/sale` → 404; полоса TTL — сколько осталось.
20. Срок вышел: промах → `/promo` ✓ → 🟡 🟢. Ярлык **TTL · bounded staleness**. Голосом: TTL — не «сколько
    хранить», а сколько мы готовы врать в худшем случае.

**Кейс 2 из 2** — плашка: «Ссылку подхватили все. Кэш выдержит?» (новый старт: в базе и Redis `/sale`)
- *Кэш как есть*
21. 200 000 кликов/с. Redis — кластер из 4 узлов; ключ `x7Kp2` в слоте узла 3: полоса узла 3 за
    потолком, остальные — низко (обслуживают другие ключи). Браузеры: «⏳». Рифма с хуком.
22. → 🔴 🟢. Ярлык **Hot key**. Postgres: «Ну хоть не я.»
- *Больше узлов* — штамп
23. 6 узлов; слот переехал на узел 5 — тонет узел 5 → 🔴 🟢. Голосом: узлы делят ключи, а не один ключ;
    реплики дали бы копии, но у каждой свой потолок и своё отставание.
- *Локальный кэш L1* — штамп
24. У каждого пода карман `x7Kp2 → /sale` на 5 с (остаток разный: A 1 с, B 2 с, C 4 с). В Redis — примерно
    по запросу от пода раз в 5 с: полоса узла зелёная → 🟢, вторая лампа пустая. Ярлык **Local cache · L1**.
25. Автор правит: A `COMMIT` → `DEL` в Redis → чистит свой L1. У B и C в кармане ещё `/sale` → 404.
    Голосом: «Это снова stale cache» (рифма с актом 1.2), сразу сбросить копии некому.
26. Часы +4 с (одним шагом): срок L1 у B вышел → Redis промах → база → `/promo` ✓ и кладёт в Redis; у C L1 тоже
   истёк → берёт `/promo` уже из Redis → лампа свежести 🟡.
- *L1 + рассылка «сбрось»* — штамп «⟲ Вернёмся: до правки»
27. A: `COMMIT` → `DEL` → `PUBLISH «сбрось x7Kp2»` (строго в этом порядке); B и C чистят L1 за миллисекунды.
    Доставляет Redis: стрелка A → рамка Redis (подпись «канал») → B, C; поды друг друга не знают. Голосом: все поды
    подписаны на канал «сбрось»; публикация раньше DEL — B и C взяли бы старое из Redis ещё на 5 с. Альтернатив
    Redis (NATS, `LISTEN/NOTIFY`) не называем — решение пользователя 22.10.
28. Следующий клик: L1 промах → Redis → база → `/promo` ✓ ✓ → 🟢 🟢. Ярлык **Pub/Sub invalidation**.
    Голосом: паттерн — двухуровневый кэш с инвалидацией через Pub/Sub; доставку Pub/Sub не гарантирует —
    короткий срок L1 остаётся страховкой.

**Итог — повтором образов:** кадр 6 (Redis отвечает, база спит) → кадр 17 (база, потом удалить) → кадр 20
(TTL ограничил враньё) → кадр 28 (рассылка + срок L1).

## Технические оговорки (tech-expert, 21.10)
- Postgres на чтении по ключу держит десятки тысяч запросов/с; в хуке тонет **пул соединений** (очередь
  за соединением, задержка растёт нелинейно), а не CPU и не диск. Ёмкость числом в кадре не называем.
- Узел Redis — один поток команд, ~100–200 тыс. простых GET/с без pipelining: 200 тыс./с на один ключ
  топит узел, 20 тыс. — нет. Ключ → слот `CRC16(key) mod 16384` → один мастер; решардинг переносит
  слот целиком.
- Чтение в Postgres не ждёт чужую транзакцию (MVCC): `SELECT` B в 13 видит последнее закоммиченное.
- DEL лучше SET не из-за гонки с читателем (она одинакова), а из-за двух правок подряд (SET'ы в обратном
  порядке) и «не кладём то, что никто не прочтёт». Цена DEL — всплеск промахов горячего ключа.
- Остаточная гонка «база → DEL» возможна, только если ключа в кэше не было до правки — в описание.
- «Раз в 5 с от пода» — без singleflight при истечении L1 все одновременные запросы пода идут в Redis.
- Pub/Sub — at-most-once: сообщение во время разрыва соединения потеряно; страховка — TTL L1.

## В описание под видео (не в ролик)
SET вместо DEL и гонка двух правок (версия в значении, условный SET через Lua); отложенное повторное
удаление; остаточная гонка «прочитал до COMMIT, положил после DEL»; cache stampede (singleflight,
`SET NX`, stale-while-revalidate, разброс TTL); negative caching и фильтр Блума; TTL ≤ `expires_at`;
302, а не 301; реплики Redis (`READONLY`), размножение ключа, CDN; Pub/Sub at-most-once → при
переподключении сбросить весь L1, Redis Streams, `SPUBLISH`; `CLIENT TRACKING` (Redis 6+); инвалидация
из WAL (CDC); пул соединений и `max_connections`; read-реплики Postgres.

## В описание: что осталось за кадром (tech-expert, 21.10)
- Короткий TTL у горячего ключа: в момент истечения в базу идёт не один запрос, а все промахи до SET соседа
  (cache stampede).
- «База, потом удалить» не закрывает гонку полностью: читатель промахнулся до COMMIT, а SET сделал после DEL —
  старая копия ляжет на весь срок. Редко; страхует TTL.
- Рассылка после DEL оставляет узкое окно: B сделал GET до DEL, а в L1 положил после рассылки — закрывает
  короткий срок L1.
- 20 тыс. чтений по первичному ключу Postgres тянет сам; в хуке кончаются соединения пула (упрощение).
- Голос говорит просто «ссылка»; сервис коротких ссылок назван один раз в хуке как источник задачи (решение
  пользователя 21.10). Код ссылки на экране — ключ Redis; голос его не читает.
- Redis Pub/Sub — at-most-once: отключённый подписчик сообщение теряет, поэтому у L1 короткий срок; при
  переподключении под сбрасывает весь L1. Ещё одна потеря — A упал между DEL и PUBLISH; тоже закрывает срок L1.
- PUBLISH доходит и до самого A (он тоже подписан) — сброс пустого L1 безвреден; на картинке стрелки только к B и C.
- (27.10) Промах после DEL читает promo только с primary: чтение с отстающей реплики Postgres вернёт sale и положит его
  в Redis на весь срок.
- (27.10) Redis удаляет просроченные ключи лениво и фоновой выборкой, а не по таймеру; гарантия — просроченный ключ не
  отдаётся. В Redis Cluster слоты при добавлении узлов переносят решардингом, сами они не переезжают.

## Обсуждения
- 21.10, tech-expert (сценарий v1): стрелка промаха — мимо Redis (cache-aside, не read-through); свежесть — против

- 21.10, tech-writer: без самодельных метафор («щель», «карман» — в голосе; «карман» остался только словом
