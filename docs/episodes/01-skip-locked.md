# Эпизод 01 — «Почтальоны и одна посылка»

Тема: несколько подов разбирают общую очередь задач в Postgres. Дубли → `FOR UPDATE` →
`SKIP LOCKED` → lease → зомби-под и проверка владельца.

Статус: **черновик сюжета, MVP не сделан.**

## Мир
- Сортировочный цех. Стеллаж с посылками = таблица `tasks`, полка = строка (`id`, `status`,
  позже `locked_by`, `lease_until`).
- Поды = курьеры-гоферы A, B, C. Постгрес = ворчливый кладовщик-слон (сквозные реплики).

## Акты
| # | акт | что видно | вывод для зрителя |
|---|---|---|---|
| 0 | Хук | у двери клиента два курьера с одной посылкой, «списано дважды» | вот к чему придём |
| 1 | Нормальный мир | курьеры по очереди: `SELECT ... status='new'` → `UPDATE status='in_progress'` | работает… пока везёт со временем |
| 2 | Час пик | A и B читают одну полку одновременно; стоп-кадр, красное «окно гонки» между SELECT и UPDATE | чтение и запись — два действия, не одно |
| 3 | Наивные фиксы | «перепроверим статус» — гонка сдвинулась; `sync.Mutex` — замок на собственном рюкзаке, B и C его не видят | мьютекс живёт внутри одного пода |
| 4a | `FOR UPDATE` | на полке висячий замок, B ждёт в очереди, растут часы | корректно, но все стоят друг за другом |
| 4b | `SKIP LOCKED` | B видит замок, пожимает плечами, берёт следующую | параллельно и без дублей |
| 5 | Lease | короткая транзакция клеит стикер «Pod B до 12:00:30»; B падает (OOM), стикер сгорает, берёт C | не держим транзакцию на время работы |
| 6 | Зомби | B очнулся и тоже доставил; фикс — `UPDATE ... WHERE id=$1 AND locked_by=$me` + идемпотентность | at-least-once, а не exactly-once |
| 7 | Шпаргалка | карточка с SQL и ответом для собеседования | — |

## Шпаргалка (черновик)
```sql
UPDATE tasks SET status='in_progress', locked_by=$1, lease_until=now()+'30s'
WHERE id IN (SELECT id FROM tasks
             WHERE status='new' OR (status='in_progress' AND lease_until < now())
             ORDER BY id LIMIT 10 FOR UPDATE SKIP LOCKED)
RETURNING *;
```
