# Эпизод 01 — «Почтальоны и одна посылка»

Тема: несколько подов разбирают общую очередь задач в Postgres (READ COMMITTED). Гонка →
условный UPDATE → `FOR UPDATE` → `SKIP LOCKED` → lease-талон → зомби-воркер, токен захвата
и идемпотентность у получателя.

Статус: **сценарий v3 (после показа MVP и рецензий) — правки в работе.**
MVP: `npm run dev` → http://localhost:5173 (кадр по ссылке: `#step=N`).

## Арка
Хук — провал из финала: «Каждый был уверен, что посылка его. Клиент получил дважды». Ролик чинит
одно за другим, на SKIP LOCKED — ложный хэппи-энд, затем курьер зависает или падает, и в финале
мы у той же двери: клиент «Уже получил, спасибо». Главный «ага»: **склад бережёт свою запись, а
двойной эффект ловит получатель.**

## Мир и персонажи
- Сортировочный цех. Стеллаж = таблица `tasks`, полка = строка (`id`, `status`, `claim_token`,
  `lease_until`).
- **Курьеры-гоферы A, B, C** = поды. B — неудачник эпизода: проигрывает толпу, стоит в конвое,
  зависает, падает, становится зомби.
- **Кладовщик-слон Postgres** — ворчит, работает строго по правилам, никого не жалеет. Хвалит
  один раз за эпизод — на SKIP LOCKED.
- **Двери клиентов** — у каждого заказа своя, справа на уровне его полки. Норма — курьеры
  разъезжаются по разным дверям; дубль — двое у одной. Хук и финал — дверь заказа 1 (рифма).
- **Табличка «READ COMMITTED»** и **часы склада** — во всех кадрах. Часы не идут назад.
- Правило подачи: картинка раньше термина (замок → FOR UPDATE, пожал плечами → SKIP LOCKED,
  талон → lease).

## Подача (v3)
- **В ролике текста минимум** (правило CLAUDE.md «Текст в кадре»): сюжет несут стрелки, картинка и
  короткая реплика; подпись ≤ 2 строк и только где без неё непонятно. Подробности — в шпаргалке.
- **Стрелки** — только из состояния модели: полка → под (посылка в руках), под → 🚪 своего заказа (доставка;
  дубль — красная, отклонённый повтор — серая с ✕), пунктир под ⇢ полка (ждёт замок). Замок,
  взятый при перепроверке, но не вернувший строку, — полый серый, не 🔒.
- **SQL-панель** — только где SQL надо прочитать; транзакция видна целиком (`BEGIN` … `COMMIT`).
- Время кадра = 1.5 с + 0.035 с × весь текст кадра (подпись, титр, реплики, SQL); шпаргалка —
  фиксированно. Цель ≤ 3:20, держит тест.

## Кадры (v3)
«—» — без подписи. Реплики: **К** — кладовщик, **Кл** — клиент.

**0. Хук**
1. B и C у двери заказа 1 с одной и той же посылкой (без идемпотентности — обе приняты); на стеллаже
   без талонов и сроков, Pod A за кадром — зритель их ещё не знает. Подпись «Каждый был уверен, что посылка его.» Кл: «Мне два одинаковых заказа?»
2. Титр-рамка «Competing consumers: несколько подов, одна очередь. Как не сделать работу дважды?» —

**1. Нормальный мир → час пик** (ярлык Race condition · check-then-act с кадра 7)
3. A смотрит, что свободно → #1. «Полка — задача. Курьеры — три пода одного сервиса.»
4. A: `BEGIN; UPDATE … #1; COMMIT` — посылка в руках. К: «Бери. Распишись. Следующий.» —
5. Быстрее: A у двери с #1, B берёт #2. К: «Распишись. Следующий.» —
6. «Час пик.» B у двери с #2; A смотрит → #3: «полка 3 свободна!»
7. B смотрит чуть позже → тоже #3, окно гонки. К: «Свободна. Пока что.» «A ещё ничего не записал.»
8. Стоп-кадр, титр «ОКНО ГОНКИ: SELECT ── сюда влезет сосед ── UPDATE». К: «Я показал, что было. Дальше сами.» —
9. Оба берут #3 (две стрелки из одной полки). «UPDATE по id ничего не проверяет.»
10. Оба у двери заказа 3, красная стрелка. Кл: «Две одинаковые?!» —

**2. Наивные фиксы** (ярлык Local lock ≠ distributed lock с кадра 13)
11. A и B перепроверяют: «точно new? ✓», окно гонки. «Фикс №1: перепроверить. Окно не закрылось — переехало.»
12. Оба взяли #1. —
13. B: «Я повесил замок!» К: «На свой рюкзак.» «Фикс №2: sync.Mutex.»
14. A тоже с мьютексом, оба видят #1, окно гонки. Титр «Mutex видит только свой под. Общее у подов — только база.» —

**3a. Толпа** (ярлык Compare-and-set · optimistic locking с кадра 16)
15. A, B, C видят #1. «Способ 1: «бери, только если ещё new».»
16. A: `UPDATE … AND status='new'` → 1 строка, замок. B и C — пунктир: ждут COMMIT A. «Остальные ждут его COMMIT.»
17. A: COMMIT. B и C перепроверили → 0 строк: «0 строк…» —
18. К #2 — снова толпа: C → 1, B ждал и получил 0: «Опять ноль строк…» «Дублей нет. Но кто-то всегда проигрывает.»

**3b. Конвой** (ярлык Pessimistic locking с кадра 20)
19. A: `BEGIN; SELECT … FOR UPDATE` → 🔒#1. «Способ 2: A вешает замок на #1.»
20. B и C — пунктир к #1. К: «Занято. Жди.» C: «Я стою за тем, кто стоит за тем, кто держит.» «Хотя #2–#4 свободны.»
21. Часы +3 с, A: «не тороплюсь…» «Ждут ровно столько, сколько длится транзакция A.»
22. A: COMMIT. B перепроверил #1 (бледный замок B — заперта, не взята), взял #2; пунктир C — к #1, теперь за замком B. B: «#2!» «C теперь ждёт B.»
23. B: COMMIT, C → #3. Титр «FOR UPDATE: дублей нет, но все стоят в очереди.» —

**3c. Обход** (ярлык Non-blocking claim · SKIP LOCKED с кадра 25)
24. A: `BEGIN; SELECT … FOR UPDATE SKIP LOCKED` → #1. «Способ 3: SKIP LOCKED.»
25. B: «Занято? Ну и ладно.» → #2, C → #3. К: «Наконец-то воспитанный.» —
26. Все трое отмечают и коммитят, едут. «Без дублей и без очереди.»
27. Доставили. Титр «FOR UPDATE SKIP LOCKED — занято, иди к следующей.» —

**4. Курьер завис / упал → талон** (ярлык Lease с кадра 36)
28. Титр «Починили! 🎉» —
29. Ветка 1. B: `BEGIN; SELECT … SKIP LOCKED; UPDATE …` — везёт #1, транзакция открыта. «Вариант 1: держать транзакцию, пока везём.»
30. 12:00:05, B завис: «📞 Ваш звонок очень важен для нас…» К: «Упал бы — соединение закрылось бы, замки бы снял. А он жив.» «B завис на внешнем API.»
31. 12:10:00, A и C обходят #1 (🔒B). «10 минут. Все обходят #1. Её никто не везёт.»
32. Под B перезапустили (kubectl): соединение закрылось → ROLLBACK, замок снят, #1 снова new. «Убили под — замок снялся сам.» —
33. Ветка 2 (часы идут дальше). B: `BEGIN; … UPDATE in_progress; COMMIT` — замков нет. «Вариант 2: отметить «в работе» и сразу COMMIT.»
34. B падает (исчезает). 12:11:00, A и C смотрят: #1 `in_progress`, не new — никто не берёт. К: «В работе. Жив ли он — не знаю.» «#1 «в работе» навсегда.»
35. Новый стеллаж (перелистывание, часы идут). Титр «Lease: при захвате — «в работе» + срок по часам БД. Не успел — берёт другой.» —
36. 12:11:10. B берёт #1 одним оператором — талон #7f3a, срок возвращается в `RETURNING`. К: «Талон до 12:11:40. По моим часам.» —
37. 12:11:15. B: «До :40 — успею.» — и завис. «B проверил срок — и снова завис.»
38. 12:11:41. К: «Срок вышел. Заберёт тот, кто спросит.» (сама база по таймеру ничего не делает) —
39. C спрашивает — и берёт просроченную #1 с талоном #c21e («фшш» — здесь). «C берёт #1.»

**5. B и C → дверь** (ярлык At-least-once · idempotency key с кадра 41)
40. 12:11:50, B отвис: «Талон до :40, я проверял в :15!» К: «Проверял — в :15. Сейчас :50.» —
41. Старый B у двери, доставил; `UPDATE … AND claim_token='7f3a'` → 0 строк. B: «…а посылку я уже отвёз.» К: «Талон #7f3a сгорел.» «Запись цела. Посылка уже у клиента.»
42. C у той же двери, повтор отклонён (серая стрелка ✕), UPDATE → 1. Кл: «Заказ 1? Уже получил. Спасибо.» —
43. Тишина. К в камеру: «Ровно один раз? Это не ко мне. Это к двери.» —
44. Титр «Склад бережёт свою запись. Двойной эффект ловит получатель.» —

**6. Шпаргалка** (текста много — здесь можно)
45. Запрос целиком (12 с).
46. «Что мы прошли» — ярлык → расшифровка (15 с).
47. «Что спросят на собесе» (15 с) — см. ниже.

## Шпаргалка
```sql
-- захват (одним оператором, autocommit — now() = время БД)
UPDATE tasks
   SET status='in_progress', claim_token=gen_random_uuid(),
       attempts = attempts + 1, lease_until = now() + interval '30s'
 WHERE id IN (SELECT id FROM tasks
               WHERE (status='new' OR (status='in_progress' AND lease_until < now()))
                 AND attempts < 5
               ORDER BY id LIMIT 10
               FOR UPDATE SKIP LOCKED)
RETURNING id, claim_token, lease_until;

-- завершение и продление — только по своему талону
UPDATE tasks SET status='done'                         WHERE id=$1 AND claim_token=$2;
UPDATE tasks SET lease_until = now() + interval '30s'  WHERE id=$1 AND claim_token=$2;
```
- индекс: частичный `ON tasks(id) WHERE status='new'` + индекс по `lease_until` для просроченных;
- heartbeat: долгая задача продлевает талон;
- `attempts ≥ 5` → полка возвратов (dead-letter);
- SKIP LOCKED — не строгий FIFO;
- эффекты — идемпотентны (ключ = бизнес-id заказа); гарантия at-least-once.

«Что спросят на собесе» (кадр 47):
- `FOR UPDATE` держит замок только внутри транзакции: в Go — `tx.QueryRow`, не `db.QueryRow`
  (иначе autocommit, замок снят сразу, следующий запрос — с другого соединения пула).
- Условный UPDATE — CAS: проверять `RowsAffected()`; проигравший ждёт COMMIT победителя.
- Держать транзакцию на всю работу: занятое соединение, VACUUM, замок до таймаута —
  `idle_in_transaction_session_timeout` / `transaction_timeout` (PG17; по умолчанию выключены);
  пропавший узел — до TCP keepalive (из ОС, на Linux ~2 ч) или `tcp_user_timeout`.
- Закоммитили `in_progress` и упали — задача застряла: нужен lease. Ставится при захвате:
  `lease_until IS NULL` условие `lease_until < now()` не поймает.
- Пауза между проверкой срока и действием (троттлинг CPU в контейнере, своп/SIGSTOP, зависший
  вызов) — тот же check-then-act. Запись в БД защищает токен в WHERE, внешний эффект — только
  идемпотентность.
- Владелец — токен захвата, а не имя пода: имя повторяется (несколько горутин в поде, тот же
  hostname после рестарта в StatefulSet, тот же воркер взял задачу снова). Новый токен — на каждый захват.
- Идемпотентность у получателя — тоже атомарно: `INSERT … ON CONFLICT DO NOTHING` по ключу в
  одной транзакции с самим эффектом.
- Compare-and-set «оптимистичен» в чтении: запись всё равно ждёт незакоммиченного соперника.

Ответ на собесе: «Захват — одним `UPDATE … WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED)` с
lease и токеном захвата; транзакцию на время работы не держим; завершение — по токену; побочные
эффекты идемпотентны, потому что доставка at-least-once».

## Технические оговорки (tech-expert)
- Всё в READ COMMITTED. Условный UPDATE после ожидания перепроверяет WHERE на новой версии строки.
- `FOR UPDATE … LIMIT 1` после ожидания не возвращает строку, переставшую подходить, и берёт
  следующего кандидата из того же снимка (поэтому «конвой», а не «ушёл ни с чем»).
- При падении процесса с открытой транзакцией соединение закрывается, Postgres откатывает её и
  снимает блокировки; пропал узел/сеть — бэкенд держит замки до TCP keepalive. Живой зависший —
  до `idle_in_transaction_session_timeout` (по умолчанию нет).
- Lease нужен в обоих вариантах: держим транзакцию — дорого и замок у зависшего; коммитим
  `in_progress` — упавший оставляет задачу навсегда.
- Часы зависшего процесса не стоят: опасна пауза между проверкой срока и действием.
- Просрочку lease база не «исполняет» по таймеру — её замечает следующий захват (`lease_until < now()`).
- Владелец — токен захвата, не имя пода. Проверка токена бережёт только запись в БД. В ролике
  перехватывает другой под (C), поэтому довод «почему не имя» — только в шпаргалке.

## Ярлыки-термины (проверены tech-expert)
Рамка после хука: «Competing consumers: несколько подов, одна очередь. Как не сделать работу дважды?»

| акт | ярлык (с кадра, где механика уже видна) |
|---|---|
| 1 | Race condition · check-then-act |
| 2 | Local lock ≠ distributed lock |
| 3a | Compare-and-set · optimistic locking |
| 3b | Pessimistic locking |
| 3c | Non-blocking claim · SKIP LOCKED |
| 4 | Lease |
| 5 | At-least-once · idempotency key |

Шпаргалка — три кадра: запрос целиком, «Что мы прошли» (ярлык → одна строка расшифровки), «Что спросят на собесе».
Отвергнуто: «fencing token» в акте 5 (у Клеппмана — монотонный номер, проверяемый внешним ресурсом;
у нас — CAS по токену владельца в той же БД, а дверь он как раз не защищает); «idempotency key →
at-least-once» (стрелка переворачивает причину); «без дублей» в рамке (финал показывает дубль
доставки, который гасит получатель).
