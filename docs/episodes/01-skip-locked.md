# Эпизод 01 — «Конкурентная обработка задач»

Тема: несколько подов разбирают общую очередь задач в Postgres (READ COMMITTED). Две главы:
**кейс 1** — как раздать задачи без дублей (гонка → CAS → `FOR UPDATE` → `SKIP LOCKED`; мьютекс убран 19.10 —
это ошибка кода, а не инженерное решение, решение пользователя);
**кейс 2** — исполнитель завис (lease → зомби → идемпотентность у приёмника).

Статус: **v6 (19.10) — закадр по правкам пользователя (контекст в хуке, FOR UPDATE и SKIP LOCKED объяснены),
без мьютекса, 48 кадров; субтитр — по фразам в одну строку.** Актуальный закадр — `01-narration.md`
(выгрузка из script.ts, номера = кадры плеера). Разделы «Кадры (v4.1)» и «Закадр v5» ниже — история,
нумерация там старая.
Табло попыток в каждой главе: кейс 1 «без дублей / без ожидания», кейс 2 «не застревает / письмо одно».
MVP: `npm run dev` → http://localhost:5173 (кадр по ссылке: `#step=N`).

## Арка
Две главы, каждая открывается полноэкранной плашкой «КЕЙС N из 2» с вопросом; номер кейса висит в
углу до конца главы. Хук — гонка в чистом виде: трое схватили одну задачу, ушло три письма.
Кейс 1 чинит раздачу: дубли убирает условный UPDATE (CAS), `FOR UPDATE` тоже корректен, но строит
очередь, `SKIP LOCKED` — про скорость, а не про корректность. Кейс 2 ломает «починили»: исполнитель
завис, задачу перехватили по сроку, зомби очнулся — **в таблице одна строка `done`, а писем два**
(рифма кадров 4 и 24). Главный «ага»: **база бережёт свою запись, двойной эффект гасит приёмник.**

## Обложка и финальная карточка (`Scene.meta`, 18.10)
- Обложка (v6, 19.10): «Конкурентная обработка задач» / «Как несколько подов делят одну очередь без
  дублей, простоев и зависших задач». Название — инженерная проблема, а не частный случай и не база:
  шаблон существует безотносительно Postgres, серия — по проблеме на эпизод (пользователь; отброшено
  «Очередь задач на Postgres» — «причём тут Postgres»). «Без дублей» — про запись в базе (задачу закрывает один владелец
  токена), дубль письма гасит получатель — финал это оговаривает (tech-expert). Было: «Три пода и одна
  задача» / «Как сделать так, чтобы на один заказ приходило одно письмо».
- Финал: «База бережёт свою запись, а повтор письма гасит получатель по ключу».
- Цепочка scriptwriter → tech-writer → tech-expert. Отброшено: «Как не отправить одно письмо три
  раза» (под при at-least-once **отправляет** повторно — обложка обещала бы невозможное, кадр 41);
  «Задачу берёт один под, но письмо без ключа может уйти дважды» (переворачивает причину: два
  письма потому, что задачу выполнили двое); «…не пустит только ключ» (защищает не ключ, а
  получатель, который его проверяет).

## Мир и персонажи
- **Таблица `tasks`** — фиксированная: 6 задач «отправить письмо по заказу N», новые не появляются,
  работу надо разгрести. Колонки `id`, `status`, `claim_token`, `lease_until` (две последние —
  только в кейсе 2). Над таблицей счётчик «осталось N». `done` не удаляется: «всё разгребли» =
  все строки `done`, а не «запрос вернул пусто» (пусто бывает и когда остальное заперто).
  Каждый способ кейса 1 пробуется на свежих 6 задачах — сравнение на одинаковом старте.
- **Поды A, B, C** стоят на месте (столбик справа от таблицы), никуда не ездят. У каждого свой
  цвет. B — неудачник: проигрывает CAS, стоит в конвое, зависает, становится зомби.
- **Кладовщик-слон Postgres** — ворчит, работает строго по правилам. Хвалит один раз — на SKIP LOCKED.
- **Приёмник «📨 Почта»** справа: журнал отправленных писем (`заказ 3`). Дубль — второе письмо
  красным. Это внешний мир: таблица его не видит. Идемпотентность — только в финале кейса 2.
- **Табличка «READ COMMITTED»** и **часы БД** — во всех кадрах. Часы не идут назад.
- Правило подачи: картинка раньше термина.

## Подача (v4)
- **В ролике текста минимум** (CLAUDE.md «Текст в кадре»); подробности — в шпаргалке.
- **Поды неподвижны, всё говорят стрелки и цвет** (только из состояния модели):
  смотрит — тонкая серая стрелка под → строка; взял — строка в цвете пода + сплошная стрелка;
  ждёт замок — пунктир + тикающие часики над подом; пропустил (`SKIP LOCKED`) — дуга мимо занятой
  строки; завис — под серый; отправил — стрелка под → Почта, новая запись в журнале.
- **0 строк у CAS = «проиграл»** (✕ у пода) — рисуется иначе, чем «задач нет».
- **Табло попыток** под подами: каждая попытка главы — строка с двумя лампами (🔴🟡🟢), лампа
  загорается в кадре, где результат уже виден. Близость к решению видна без подписей. Лампы сверяет
  с моделью тест («табло не врёт»).
- Замок, взятый при перепроверке, но не вернувший строку, — полый серый, не 🔒.
- **SQL-панель** — только где SQL надо прочитать; транзакция видна целиком (`BEGIN` … `COMMIT`).
- Время кадра = 1.5 с + 0.035 с × весь текст кадра; плашки кейсов — 2 с; шпаргалка — фиксированно.
  В углу во время главы — только «Кейс N», вопрос — только на плашке.
  Цель ≤ 3:20, держит тест.

## Кадры (v4.1 — раскадровка по актам)

**1.1 Гонка** (ярлык Race condition · check-then-act с кадра 4)

4. Оба `UPDATE … WHERE id=1`, оба отправили письмо. «В таблице одна строка. Писем — два.»

**1.2 Мьютекс** — убран 19.10 (решение пользователя: ошибка кода, а не инженерное решение).

**1.3 Условный UPDATE** (ярлык Compare-and-set · optimistic locking с кадра 9)
7. Свежие 6 задач. A, B, C видят #1. —
8. A: `BEGIN; UPDATE … AND status='new'` → 1 строка (письмо — только после COMMIT). B и C — пунктир: ждут COMMIT A. —
9. A: `COMMIT`, письмо. B и C перепроверили → 0 строк (✕ «проиграл»). «Дублей нет — их убрал этот WHERE.»
10. Новый круг: B → #2, C снова ✕ → #3. К: «Кто-то всегда проигрывает.» —

**1.4 FOR UPDATE** (ярлык Pessimistic locking с кадра 12)
11. Свежие 6 задач. A: `BEGIN; SELECT … ORDER BY id LIMIT 1 FOR UPDATE` → 🔒#1. B и C — пунктир к #1.
    К: «Занято. Жди.» «Хотя #2–#6 свободны.»
12. A: `COMMIT`. B перепроверил #1 — она уже не подходит, но замок на ней теперь B (полый), B взял #2.
    Пунктир C по-прежнему к #1 — ждёт уже B. «Конвой: ждут друг за другом.»
13. B: `COMMIT` → C берёт #3. —

**1.5 SKIP LOCKED** (ярлык Non-blocking claim · SKIP LOCKED с кадра 15)
14. Свежие 6 задач. Все трое одним оператором; в панели крупно:
    `UPDATE … WHERE id IN (SELECT id … WHERE status='new' LIMIT 1 FOR UPDATE SKIP LOCKED)`. —
15. A → #1; B — дуга мимо #1 → #2; C — дуга → #3. К: «Наконец-то воспитанный.» —
16. Ускоренно: #4–#6, все `done` → «осталось 0», по одному письму на заказ. Титр «Дубли убирает
    WHERE status='new' под замком. SKIP LOCKED — чтобы не стоять.» —

## Закадр v5 — история; актуальный — `01-narration.md` (этап 5 полировки: подача по learning-designer, тексты — scriptwriter → tech-writer → tech-expert)
Диктор — браузерный синтез: начинает через 0.5 с после показа кадра, после фразы — 0.7 с паузы.
Произношение латиницы — `PRONOUNCE` в script.ts. Номер = кадр плеера (#step=N); в скобках — акт, фокус, штамп.
Что изменилось с v4.3: норма 4–5 до первой поломки; плашка главы 2 «Под замолчал. Жив ли он?» и «?» у B
до конца главы (World.doubt); нарезка 29→31/32, 32→35/36, 33→37/38, 40→45/46; часы прыгают на час на 34;
мысль B «Запас есть — успею» с 39 до 42 (устаревшая проверка), строка в цвет владельца токена,
бледная стрелка B после перехвата, плашка «≠» до конца сцены (World.clash), ключ у подов на 45;
итог 48–50 — повтор кадров 41, 43, 46; COMMIT объяснён на 14; «воркер» → «под».
Разбор текстов — `docs/reviews/01-stage5-texts-draft.md` (в т. ч. правки по проверке learning-designer v5:
критерии табло названы голосом на 7 и 28, «кейс» вместо «глава», сокращены 35 и 47, силуэт упавшего B).

1. [0. Хук] Три пода взялись за одну задачу — и ушло три одинаковых письма.
2. [Знакомство · фокус: table] Разберёмся. Слева — таблица задач в Postgres: в ней шесть записей, и у всех статус «новый».
3. [Знакомство · фокус: A, B, C] В центре — три пода одного сервиса. Каждый берёт задачу из таблицы и отправляет письмо.
4. [Знакомство · фокус: A, row:1] Сначала посмотрим, как всё работает в норме: под A берёт первую задачу.
5. [Знакомство · фокус: A, mail, row:1] Он отправляет письмо и отмечает задачу выполненной. Итог: на одну задачу — одно письмо.
6. [Знакомство · фокус: mail] Каждая задача — это письмо по конкретному заказу, и уйти оно должно ровно один раз. Если ушло два письма, это дубль и брак.
7. [Кейс 1] В первом кейсе мы раздаём задачи и следим за двумя вещами: чтобы не было дублей и чтобы никто не простаивал в ожидании.
8. [1.1 Гонка · фокус: A, B, row:1] Двое читают таблицу и видят одну и ту же задачу. Между чтением и записью открывается окно гонки.
9. [1.1 Гонка · фокус: A, B, mail, board] Оба отправили по письму. Это классический race condition: сосед вклинился между проверкой статуса и действием.
10. [1.2 Мьютекс · фокус: A, B] Попробуем закрыть окно мьютексом из пакета sync. Но он работает только внутри одного процесса, а поды у нас разные.
11. [1.2 Мьютекс · фокус: mail, board] И снова ушло два письма. Мьютекс видит только горутины собственного процесса, а нам нужна блокировка, общая для всех подов.
12. [1.3 Условный UPDATE · фокус: table] Значит, проверять условие должна сама база: обновляем задачу, только если её статус всё ещё «новый».
13. [1.3 Условный UPDATE · фокус: A, row:1, sql] Все трое отправляют UPDATE, но база пропускает только под A.
14. [1.3 Условный UPDATE · фокус: B, C, row:1] Поэтому B и C висят в ожидании, пока A не сделает COMMIT и не зафиксирует транзакцию.
15. [1.3 Условный UPDATE · фокус: B, C, sql] Когда A делает COMMIT, поды B и C перепроверяют условие и видят, что статус уже изменился.
16. [1.3 Условный UPDATE · фокус: A, mail] В итоге письмо уходит ровно одно. Это подход compare-and-set, или оптимистичная блокировка: мы не запирали строку заранее.
17. [1.3 Условный UPDATE · фокус: B, C] На следующем круге всё повторяется: B успевает забрать вторую задачу, а C снова остаётся ни с чем.
18. [1.3 Условный UPDATE · фокус: board] Дублей при этом нет, но проигравшие поды работают вхолостую.
19. [1.4 FOR UPDATE · фокус: A, row:1, sql] Тогда заблокируем строку заранее через FOR UPDATE — это пессимистичный подход. Под A запирает первую строку.
20. [1.4 FOR UPDATE · фокус: B, C, row:1] Но B и C встают за ним в очередь, хотя рядом полно свободных задач!
21. [1.4 FOR UPDATE · фокус: B, row:2] Под A делает COMMIT. Под B просыпается, видит, что первая задача уже недоступна, и берёт вторую.
22. [1.4 FOR UPDATE · фокус: C, row:1] Теперь под C вынужден ждать пода B: при перепроверке B запер первую строку и держит замок до своего COMMIT. Это затор на ровном месте — head-of-line blocking.
23. [1.4 FOR UPDATE · фокус: board] Так по цепочке пройдут все задачи: дублей не будет, но каждый под вынужден ждать предыдущего.
24. [1.5 SKIP LOCKED · фокус: A, row:1, sql] Чтобы убрать простои, добавим SKIP LOCKED: он просто пропускает уже заблокированные строки. Под A берёт первую задачу.
25. [1.5 SKIP LOCKED · фокус: B, row:2] Теперь под B видит, что первая строка занята, спокойно проходит мимо и берёт вторую.
26. [1.5 SKIP LOCKED · фокус: C, row:3] Под C тут же забирает третью. Никто никому не мешает — это неблокирующий захват, non-blocking claim.
27. [1.5 SKIP LOCKED · фокус: table, mail, board] Остальные задачи разбираются точно так же. Дубли отсекает условие «статус новый», которое база проверяет под блокировкой, а ожидания убирает SKIP LOCKED.
28. [Кейс 2] Во втором кейсе один из подов замолкает, и мы не знаем, жив он или умер. Проверим, не застрянет ли задача и уйдёт ли только одно письмо.
29. [2.1 Завис или упал · фокус: B, row:1] Сначала попробуем держать транзакцию открытой всё время работы. Под B берёт задачу и зависает, ожидая ответа от внешнего сервиса.
30. [2.1 Завис или упал · фокус: clock, table, row:1] Проходит десять минут. Все остальные задачи давно обработаны, а первая всё висит: блокировка держится до закрытия транзакции пода B.
31. [2.1 Завис или упал · фокус: board] Ждать завершения такой транзакции можно часами, всё это время удерживая соединение с базой. Значит, держать транзакцию всё время работы нельзя.
32. [2.1 Завис или упал · фокус: B, row:1] Попробуем по-другому: под B переводит статус в «в работе» и сразу делает COMMIT, освобождая блокировку.
33. [2.1 Завис или упал · фокус: B] Но прямо в процессе обработки под B падает.
34. [2.1 Завис или упал · фокус: table, row:1, clock] Остальные поды видят статус «в работе» и не знают, что произошло. Зависший под со стороны не отличить от упавшего, поэтому задача так и висит «в работе» и через час, и через сутки.
35. [2.1 Завис или упал · фокус: board] Получается, оба пути тупиковые: долгая транзакция держит ресурсы базы, а задача ждёт зависшего пода.
36. [2.1 Завис или упал · фокус: board] Короткая транзакция обходится дёшево, но после падения пода задача висит навсегда. Нужен подход, который защитит и от падения, и от зависания.
37. [2.1 Завис или упал · фокус: table] Раз мы не можем узнать, жив под или нет, зададим временной лимит — срок аренды. Для этого добавим в таблицу две колонки: токен захвата и время окончания аренды.
38. [2.1 Завис или упал · фокус: B, row:1, clock] При захвате база одним запросом выдаёт поду B токен, то есть уникальную метку именно этого захвата, и фиксирует срок аренды по своим часам. Это и есть lease.
39. [2.1 Завис или упал · фокус: B, row:1] Под B проверяет срок, видит запас по времени и в этот самый момент надолго зависает.
40. [2.1 Завис или упал · фокус: row:1, clock] Время аренды истекает, но в самой строке ничего не меняется: срок — это просто значение в колонке.
41. [2.1 Завис или упал · фокус: C, row:1, sql] Зато просрочку замечает следующий захват: под C забирает подвисшую задачу и получает уже новый токен.
42. [2.2 Зомби · фокус: B, row:1, mail] Но тут под B отвисает! Ориентируясь на свою старую проверку, он отправляет письмо, даже не подозревая, что задачу у него уже отобрали. И снова сработал check-then-act.
43. [2.2 Зомби · фокус: B, row:1, sql] Под B пытается отметить задачу выполненной, но база отклоняет запрос: токен в строке уже чужой! Вот только письмо уже улетело, и отменить его нельзя.
44. [2.2 Зомби · фокус: C, mail, row:1] Вслед за ним письмо по той же задаче отправляет новый владелец — под C. Итог: запись в базе одна, а писем снова два. База защитила свои данные, но не внешнюю отправку.
45. [2.2 Зомби · фокус: B, C, mail] База не может отозвать письмо, поэтому защитим внешнюю систему отдельно. Вернёмся назад, пока B ещё спит, и добавим ключ идемпотентности — например, номер заказа.
46. [2.2 Зомби · фокус: mail] Теперь оба письма уходят с одинаковым ключом. Какое бы из них ни пришло в сервис рассылки вторым, Почта распознает дубль и просто вернёт прежний ответ.
47. [2.2 Зомби · фокус: board] Раз медленный под не отличить от мёртвого, задачу иногда приходится забирать у ещё живого, а терять письмо нельзя. Так мы приходим к гарантии at-least-once: повторные отправки неизбежны, и защищаться от них должен сам получатель.
48. [Итог · фокус: row:1, clock, C, board] Подведём итог. Срок аренды, или lease, не даёт задаче зависнуть навсегда: просроченную работу перехватит первый же под, который придёт за задачей.

## Шпаргалка (в ролик не входит — материал для описания под видео)
```sql
-- захват (одним оператором, autocommit — now() = время БД)
UPDATE tasks
   SET status='in_progress', claim_token=gen_random_uuid(),
       attempts = attempts + 1, lease_until = now() + interval '30s'
 WHERE id IN (SELECT id FROM tasks
               WHERE (status='new' OR (status='in_progress' AND lease_until < now()))
                 AND attempts < 5
               ORDER BY id LIMIT 10
               FOR UPDATE SKIP LOCKED)
RETURNING id, claim_token, lease_until;

-- завершение и продление — только по своему талону
UPDATE tasks SET status='done'                         WHERE id=$1 AND claim_token=$2;
UPDATE tasks SET lease_until = now() + interval '30s'  WHERE id=$1 AND claim_token=$2;
```
- индекс: частичный `ON tasks(id) WHERE status='new'` + индекс по `lease_until` для просроченных;
- heartbeat: долгая задача продлевает талон;
- `attempts ≥ 5` → полка возвратов (dead-letter);
- SKIP LOCKED — не строгий FIFO;
- эффекты — идемпотентны (ключ = заказ + тип письма, у внешнего API — `Idempotency-Key`; повтор
  с тем же ключом возвращает сохранённый ответ, а не ошибку);
  гарантия at-least-once. Не «проверь `status='done'` перед отправкой» — это снова check-then-act.

«Подводные камни: на что смотреть в коде» (кадр 29):
- `FOR UPDATE` держит замок только внутри транзакции: в Go — `tx.QueryRow`, не `db.QueryRow`
  (иначе autocommit, замок снят сразу, следующий запрос — с другого соединения пула).
- Условный UPDATE — CAS: проверять `RowsAffected()`; проигравший ждёт COMMIT победителя.
- Держать транзакцию на всю работу: занятое соединение, VACUUM, замок до таймаута —
  `idle_in_transaction_session_timeout` / `transaction_timeout` (PG17; по умолчанию выключены);
  пропавший узел — до TCP keepalive (из ОС, на Linux ~2 ч) или `tcp_user_timeout`.
- Закоммитили `in_progress` и упали — задача застряла: нужен lease. Ставится при захвате:
  `lease_until IS NULL` условие `lease_until < now()` не поймает.
- Пауза между проверкой срока и действием (троттлинг CPU в контейнере, своп/SIGSTOP, зависший
  вызов) — тот же check-then-act. Запись в БД защищает токен в WHERE, внешний эффект — только
  идемпотентность.
- Владелец — токен захвата, а не имя пода: имя повторяется (несколько горутин в поде, тот же
  hostname после рестарта в StatefulSet, тот же воркер взял задачу снова). Новый токен — на каждый захват.
- Идемпотентность у получателя — тоже атомарно: `INSERT … ON CONFLICT DO NOTHING` по ключу в
  одной транзакции с самим эффектом.
- Compare-and-set «оптимистичен» в чтении: запись всё равно ждёт незакоммиченного соперника.

Итоговая формулировка: «Захват — одним `UPDATE … WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED)` с
lease и токеном захвата; транзакцию на время работы не держим; завершение — по токену; побочные
эффекты идемпотентны, потому что доставка at-least-once».

## Технические оговорки (tech-expert)
- (финал) ✓ проверки срока на полосе — по часам БД. Настоящий под сравнивает `lease_until` со своими
  часами — рассинхрон; правильно — локальный монотонный таймер от момента захвата, с запасом.
- (финал) SKIP LOCKED в ролике — захваты в явной транзакции (замок до COMMIT): при autocommit поздний
  под просто не увидит строку как `new`, SKIP LOCKED работает, когда захваты идут одновременно.
- (этап 5) «После падения блокировку база снимет сама» — верно для падения процесса пода (сокет закрыт →
  откат). Пропал узел или сеть — Postgres узнает только по TCP keepalive (~2 ч по умолчанию) или по
  `idle_in_transaction_session_timeout`; последний по сути lease на транзакцию. Долгая транзакция ещё и
  держит горизонт xmin (VACUUM не чистит).
- (этап 5) Токен — уникальная метка захвата (`gen_random_uuid()`), сравнивается только на равенство; это не
  fencing token с возрастающим номером.
- (этап 5) Ключ идемпотентности — идентификатор операции; номер заказа годится, пока на заказ одно такое
  письмо. Многие почтовые API Idempotency-Key не поддерживают — тогда ключ хранит отправитель (outbox,
  таблица отправленных), окно дубля сужается, но не закрывается. При одновременном приходе получатель
  атомарно занимает ключ, второй получает 409.
- Всё в READ COMMITTED. Условный UPDATE после ожидания перепроверяет WHERE на новой версии строки.
- `FOR UPDATE … LIMIT 1` после ожидания не возвращает строку, переставшую подходить, и берёт
  следующего кандидата из того же снимка (поэтому «конвой», а не «ушёл ни с чем»).
- При падении процесса с открытой транзакцией соединение закрывается, Postgres откатывает её и
  снимает блокировки; пропал узел/сеть — бэкенд держит замки до TCP keepalive. Живой зависший —
  до `idle_in_transaction_session_timeout` (по умолчанию нет).
- Lease нужен в обоих вариантах: держим транзакцию — дорого и замок у зависшего; коммитим
  `in_progress` — упавший оставляет задачу навсегда.
- Часы зависшего процесса не стоят: опасна пауза между проверкой срока и действием.
- Просрочку lease база не «исполняет» по таймеру — её замечает следующий захват (`lease_until < now()`).
- Владелец — токен захвата, не имя пода. Проверка токена бережёт только запись в БД. В ролике
  перехватывает другой под (C), поэтому довод «почему не имя» — только в шпаргалке.
- **Дубли убирает CAS / FOR UPDATE; SKIP LOCKED — пропускная способность**, не корректность.
- SKIP LOCKED прячет строку, только пока транзакция открыта: финал кейса 1 — `UPDATE … SET
  in_progress WHERE id IN (SELECT … SKIP LOCKED) RETURNING`, не голый `SELECT … SKIP LOCKED; COMMIT`.
- Конвой при `FOR UPDATE` — только когда все целятся в одну первую строку (`ORDER BY id LIMIT 1`).
  «Следующая по порядку» — только с `ORDER BY`; SKIP LOCKED — не строгий FIFO.
- Дубль эффекта **не виден в tasks**: оба UPDATE пишут одну строку. Отсюда приёмник вне таблицы.
- Токен и lease — только кейс 2; в кейсе 1 перезахвата нет, CAS по `status` достаточно.
  Идемпотентность (ключ) — только финал кейса 2, иначе кейс 2 теряет твист.
