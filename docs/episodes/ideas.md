### Таймауты, повторы, circuit breaker
Бронь уходит к внешнему поставщику (сеть отелей, агрегатор), а он начинает отвечать по 30 с.
Набросок арки: без таймаута поды висят, пул соединений кончается, ложится и наш поиск → таймаут → повтор сразу
добивает больного поставщика (retry storm: все поды повторяют разом) → backoff с jitter → circuit breaker: после
серии отказов не звоним вовсе, отвечаем «попробуйте позже», изредка пробуем. Идемпотентность повтора — одной
фразой со ссылкой на 08 (повтор брони не должен дать две брони).

## Distributed counter: hot row, батчинг, HyperLogLog
Рабочее название (21.10): по имени задачи, как её знают инженеры, паттерны — в подзаголовке.
Отброшены: «Почему счётчик врёт» (без паттернов), «Клики складываются, уникальные — нет» (выдаёт ответ —
оставить для финальной карточки).

Паттерны сюжета: hot row (проблема) → write-behind / батчинг (write coalescing) → sharded counter
(альтернатива) → count-distinct problem → HyperLogLog.
Откуда: тренировка system design 21.10, задача 2 лестницы —
`~/pet-projects/interview/tasks/system-design-ladder/README.md`, раздел «2. Статистика переходов».

**Подача — инженерная задача, а не system design-интервью:** не считаем RPS, объёмы и не рисуем схему
компонентов. Зритель видит конкретную поломку в коде/базе и как её чинят — как в эпизоде 01. Цифры — только
как образ на экране («очередь из 10 тыс.», «160 МБ на одну ссылку»), а не расчёт.

Набросок арки в стиле серии (хук → норма → кейсы, каждый ломает «починили»):
- **Хук:** ссылку запостили в большой канал — 10 тыс. кликов/с, `UPDATE clicks = clicks + 1` на одной строке.
  Поды встают в очередь за замком строки, пул соединений кончается — тормозит весь сервис. Рифма с эпизодом 01:
  та же строка под замком.
- **Кейс 1 — пачки:** каждый под копит клики в памяти и раз в 5 с пишет `+8431`. 20 подов → 4 записи/с вместо
  10 тыс. Цена: под упал — несколько секунд кликов пропало (статистика не деньги — ок).
  - **⟲ Иначе: sharded counter** — счётчик разбит на N строк (`x7Kp2#0..#15`), `+1` идёт в случайную, чтение —
    сумма N строк. Замок делится на 16, запись остаётся мгновенной; цена — чтение дороже, N выбирать заранее.
- **Кейс 2 — уникальные:** кто такой «уникальный» без аккаунта? Cookie-номерок (гардероб), у каждого браузера свой
  карман: Telegram и Chrome на одном телефоне — два «человека».
- **Кейс 3 — уникальные не складываются:** Android Ани попал на под №3 и под №17 — оба «новый!», в сумме 2 вместо 1.
  Рифма с хуком эпизода 01: три пода, каждый уверен в своём.
- **Кейс 4 — точный список не влезает:** 10 млн `vid` × 16 Б = 160 МБ на ссылку и на каждый день графика →
  HyperLogLog: ~12 КБ, ошибка ~1%, и главное — сливается (поды, дни → год).
- Итог-фраза (черновик): «Клики складываются, уникальные — нет».

**Решение пользователя 22.10: два эпизода** — 03 нагрузка на запись (хук + кейс 1 + sharded counter, в работе),
04 уникальные (кейсы 2–4). Открыто для 04: носитель для HLL на картинке.

## Шардирование: почему не `hash % N`
Добавлено 21.10 по просьбе пользователя. Рабочее название не выбрано.

Паттерны сюжета: `hash % N` (наивное) → массовый переезд при росте → логические шарды (фиксированное L,
таблица «шард → сервер») → consistent hashing (альтернатива) → ключ шардирования и запрос мимо него
(scatter-gather, таблица-индекс).
Откуда: тренировка system design 20.10, задача 1 лестницы (сокращатель ссылок, пункт 6.2) —
`~/pet-projects/interview/tasks/system-design-ladder/README.md`, конспект —
`~/pet-projects/interview/topics/system-design-sharding.md`.

**Подача — инженерная задача, как в «Distributed counter»:** без расчёта объёмов и схемы компонентов. Носитель —
ключи-карточки на серверах: зритель видит, какие карточки переезжают.

Набросок арки (хук → норма → кейсы):
- **Хук:** ссылок стало столько, что одна база не тянет; три сервера, ключ кладём на `hash(code) % 3`.
- **Норма:** каждый запрос по `code` идёт ровно на один сервер; уникальность кода держит обычный уникальный
  индекс внутри шарда — один код всегда на одном шарде.
- **Кейс 1 — добавили четвёртый сервер:** `% 3` → `% 4`, и с места уезжает ~75% карточек (остаются только те, где
  остаток совпал). Переезд гонит данные по сети, а кэш перед базой разом промахивается.
  - Попытка: **логические шарды** — `hash % 1024` навсегда, табличка «шард → сервер». Новый сервер забирает целые
    шарды у соседей, переезжает ровно его доля (3 → 4: 25%).
  - **⟲ Иначе: consistent hashing** — кольцо, сервер забирает дугу у соседа.
- **Кейс 2 — «мои ссылки»:** запрос по `owner_id`, а шардировали по `code` → вопрос ко всем шардам сразу
  (scatter-gather), самый медленный держит ответ. Решение — отдельная таблица-индекс `owner_id → code`, тоже
  шардированная, но по `owner_id`; цена — две записи вместо одной.
- Итог-фраза (черновик): «Шардируем по полю, по которому спрашивают, и переносим шарды, а не ключи».

Открыто: цифры (75%, 1024) и честность «кэш разом промахивается» — проверить tech-expert до сценария;
